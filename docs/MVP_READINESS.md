## Безопасность и эксплуатация

- PostgreSQL защищает аккаунт и активное членство владельца. Проверены Django Admin, обычная и массовая запись ORM, прямой SQL и передача владения. Аварийная команда требует доступа к серверу, двух разных действующих платформенных администраторов, основания и подтверждения. Имена в команде фиксируют исполнителя и согласовавшего. Независимое согласование проверяется по защищённой заявке вне приложения.
- Публичные маршруты сохраняют CSRF и проверяют организацию, область полномочий и состояние модуля на сервере. Проверены повтор токенов, смена пароля, недействительность старой сессии, попытки использовать идентификаторы чужой организации, конкурентные решения и откат вместе с аудитом. В новых и изменённых потоках просмотрены шаблоны и вывод пользовательских значений. Внешний тест периметра в целевой среде не проводился.
- Запрос сброса пароля записывает адрес в очередь без чтения аккаунта и без обращения к почте. Worker проверяет пригодность аккаунта, повторяет временные сбои ограниченное число раз и удаляет просроченные запросы при обработке. Очередь временно содержит адреса. При остановке worker письма не отправляются, а очистка ждёт возобновления обработки.
- Проверка аудитории из 102 участников измеряет массовый сценарий предпросмотра. Отправка большой партии под параллельной нагрузкой отдельно не измерялась. Защита резервных копий проверена локально. Права, хранение архивов, реальные SMTP и TLS необходимо подтвердить в пилотной среде.

## Оставшиеся требования и ограничения

- **FR-ORG-01.** Активные аккаунты, созданные до миграции, сохраняют вход. Самостоятельный сброс становится доступен после подтверждения адреса. В рабочей БД перед миграцией зафиксирован один активный аккаунт с пустым адресом, без повторов email и совпадений, различающихся регистром.
- **FR-ORG-04.** PostgreSQL блокирует деактивацию владельца. Для уже заблокированного владельца предусмотрена операторская CLI-процедура с независимым согласованием. Сброс пароля не снимает административную блокировку.
- Django Admin остаётся глобальным контуром администрирования. В тестах проверялась tenant-изоляция пользовательских API, включая запросы Django superuser без членства. Прикладные ограничения частоты действуют через PostgreSQL. Проверка публичного периметра и настройка доверенных прокси зависят от среды.
- Производственное развёртывание, подключение пилотных данных и проверка в целевом окружении требуют отдельного решения. Эксплуатационные процедуры описаны в [OPERATIONS.md](OPERATIONS.md).

## Приёмочные сценарии из исходного ТЗ

«Автотесты» означает покрытие шагов в указанных модулях. Отдельный сквозной браузерный прогон указан только там, где он подтверждён.

| ID | Исходный сценарий | Подтверждение и предел проверки |
|---|---|---|
| AT-01 | Создание Enactus и дерева Project/HR/PR/Event, перенос без циклов | Автотесты `test_organizations`, `test_departments`. Конкретный пилотный набор отделов отдельно не подтверждён. |
| AT-02 | Один аккаунт одновременно состоит в Project и PR | Автотесты `test_department_memberships` — независимые членства и вывод путей на тестовых отделах. |
| AT-03 | Руководитель видит людей Project и дочерних отделов без дублей | Автотесты `test_department_memberships`, `test_department_structure_ui`. |
| AT-04 | Запрос двух специалистов PR направляется профильному руководителю | Автотесты `test_staffing`, `test_mvp_journeys` — профильный запрос и распределение. |
| AT-05 | Прямое включение в команду и включение после принятия | Автотесты `test_staffing`. |
| AT-06 | Одна проектная задача после маршрутизации через отдел получает исполнителя | Автотесты `test_task_workflows`. |
| AT-07 | Обязательный маршрут проверки удерживает задачу от завершения | Автотесты `test_task_workflows`, `test_mvp_journeys`. |
| AT-08 | Строгая зависимость блокирует работу, информационная предупреждает | Автотесты `test_task_dependencies`. |
