# ТЕХНИЧЕСКОЕ ЗАДАНИЕ — ENACTUS OS
## Универсальная платформа-конструктор для управления организациями
### Новый проект с нуля · Codex + субагенты · MVP 1.0

**Редакция:** 3.0 (чистый старт, мультиагентная разработка)  
**Дата:** 8 ноября 2026 года  
**Статус:** полное ТЗ для самостоятельной разработки Codex в НОВОМ репозитории.  
**Первая организация:** Enactus Toraighyrov.  
**Основа:** все ранее согласованные продуктовые решения; старый код и его БД НЕ переносятся.

> Ключевой принцип: не делать «копию текущего enactusos». Построить поддерживаемый продукт **с нуля** в новом каталоге, через координацию специализированных субагентов. Codex создаёт и меняет файлы сам, запускает проверки и отчитывается за небольшие завершённые этапы; владелец проекта контролирует направления, архитектуру и итоговый код.

# 0. ОБЯЗАТЕЛЬНЫЕ указания Codex перед стартом

## 0.1. Новый изолированный репозиторий — не продолжать прошлую разработку

- Создать **совершенно новый** каталог, например `/home/stanislav/it/enactus-os-next` (или другой свободный путь, явно указанный пользователем). Внутри создать Git-репозиторий и всю структуру Django с нуля.
- Каталоги прежних экспериментов, включая `/home/stanislav/it/enactusos`, и версии `enactus-os`/`enactus-os-starter` — **только исторический контекст**. НЕЛЬЗЯ использовать их в качестве исходников, копировать оттуда миграции, модели, файлы конфигурации или `.env`. Не нужно читать их без отдельного запроса пользователя.
- Создать новую базу PostgreSQL, нового пользователя PostgreSQL, собственный compose project и **новый именованный Docker volume**. Не подключаться к старой БД `enactus_rebuild`, не использовать её volume или пароль.
- Новая разработка не должна затрагивать действующие контейнеры и данные старых проектов. Перед выбором портов проверить, не заняты ли они. Для примеров можно предложить `127.0.0.1:55433` для PostgreSQL и `127.0.0.1:8002` для dev-сайта; это **предложения**, а не обязанность использовать занятые порты.
- В свежем репозитории **все модели, API, Django-приложения, тесты, UI и миграции создаются с нуля**, а не объявляются реализованными по памяти о старом проекте.
- Не спрашивать разрешение на каждую операцию создания обычного файла в новом каталоге, но согласовывать рискованные действия и архитектурные развилки; после каждого логического инкремента давать прозрачный отчёт и контрольную точку.

## 0.2. Делегирование субагентам обязательно, когда среда поддерживает

Codex выступает **главным агентом-координатором / Tech Lead**. Для независимых задач он должен использовать доступный механизм субагентов (если доступен в текущей среде) и распределять работу по специализациям; не пытаться делать все направления одним агентом по умолчанию.

**Предусмотренные роли:** Backend/Django API, Frontend/Vanilla JS, Database/Data Model, QA & Security, DevOps/Infrastructure, Calendar/Time + Integrations (по мере необходимости), Documentation/UX (при большом объёме). Полные задания и границы владения файлами — в `docs/AGENT_ROLES.md`.

Основные правила:

1. Перед этапом координатор формулирует контракт (задача, входные данные, ожидаемые файлы и тесты) и определяет, какие работы независимы.
2. Делегирует только независимые задачи параллельно. **Никогда не разрешает двум агентам одновременно править один файл или создавать конкурирующие Django-миграции.** Для пересекающихся файлов — очередь, отдельные ветки/worktrees и интеграция главным агентом.
3. Внутренние контракты API, naming, схема данных и права доступа согласуются ДО параллельной разработки. Главный агент собирает результаты и отвечает за конечную совместимость.
4. Субагент сдаёт: перечень файлов/изменений, краткое объяснение, выполненные проверки, известные риски и явные блокеры. Координатор проводит интеграционные тесты, а не верит сообщениям «всё работает» без проверки.
5. Даже когда доступны много субагентов, не создавать их ради формальности: маленькие последовательные задания выполнять напрямую.
6. Если данная версия/режим Codex не предоставляет инструменты субагентов, сообщить об этом правдиво; **не имитировать успешную делегацию**. Использовать описанные роли как независимые последовательные ревью/этапы, либо предложить параллельные потоки Codex с отдельными Git worktrees, когда это поддерживается.

## 0.3. Граница MVP — обязательна

**В MVP:** аккаунты и организации, вложенные отделы, несколько членств одного человека, права/роли и настраиваемое наследование, проекты и запрос специалистов профильным отделам, задачи с соисполнителями/подзадачами/проверками/зависимостями, централизованные уведомления/аудит, главная панель, переключаемые прикладные модули, **полноценный календарь** (день, неделя, месяц; встречи, мероприятия, приглашения, 3 режима ответа, повторяющиеся события, дедлайны задач).

**После MVP:** официальные протоколы и их утверждение, внутренние версии файлов и библиотека документов, продвинутый конструктор аналитики/отчётов, публичные внешние интеграции/API-токены/webhooks/OAuth, шаблоны и копирование конфигураций организаций. Все будущие бизнес-правила сохранены в соответствующем разделе ТЗ.

**Подразделения Enactus для первой настройки (через UI, не в коде):** Project, HR, PR, Event. Speakers и финансы не создавать автоматически.

## 0.4. Правила качества и истинности результата

- Кодекс пишет код прямо в **новом** репозитории, не выдаёт пользователю десятки отдельных файлов для копирования.
- Один инкремент — один завершённый функциональный результат и понятный diff. Допускается параллельная работа субагентов только внутри заранее ограниченного инкремента.
- Не обещать, что модуль работает, если реально не запускались тесты и не проверялся UI/HTTP. Если среда не позволяет запустить Docker, указать точный blocker.
- Не подменять согласованную бизнес-логику технически более простой без ведома пользователя.
- Ни один флаг интерфейса не заменяет серверную проверку прав и организационной изоляции.
- Не публиковать тестовый сайт в интернет, не отправлять реальные письма/уведомления третьим лицам и не использовать реальные персональные данные без отдельного запроса.

3. Зафиксированные в новом репозитории архитектурные решения `docs/DECISIONS.md` и API-контракты, если они не конфликтуют с пп. 1–2.

# 1. Назначение и границы

**Цель MVP:** дать Enactus Toraighyrov единое место для управления организацией, подразделениями, участниками, проектами, запросами специалистов, задачами, встречами и мероприятиями. Руководитель видит статус работы, участник — свои поручения и календарные события; информация не теряется при изменении состава команды.

**Тип продукта:** универсальная multi-tenant веб-платформа с отдельными рабочими пространствами организаций. Первая пилотная организация — Enactus Toraighyrov; впоследствии, например, студенческий ректорат.

**Принцип поставки:** архитектурные контракты предусматривают расширение, но реализуем только подтверждённый MVP. Модули второго этапа не считаются готовыми и не являются условием первой эксплуатации.

**Действующие подразделения для первичного наполнения Enactus:** Project, HR, PR, Event. Финансы и Speakers пока не считаются обязательными самостоятельными отделами и могут быть добавлены через конструктор позже. Примеры людей и задач ниже условны.

# 2. Зафиксированные архитектурные решения

| Область | Утверждённое правило |
|---|---|
| Организации | Независимые рабочие пространства, данные изолированы, пользователь может состоять в нескольких организациях. |
| Структура | Произвольная вложенность подразделений, без жёстких названий «отделов»; изменения из интерфейса. |
| Членство | Один человек может состоять сразу в нескольких подразделениях, без обязательного основного. |
| Списки | Родительское подразделение показывает прямых участников и людей из вложенных отделов, не дублируя одного человека. Фактическое членство видно по подписи. |
| Каталог | Люди из других отделов той же организации могут отображаться приглушённо, если политика видимости это разрешает; приглашение в отдел — отдельное действие. |
| Полномочия | Настраиваемые роли и их область действия: своё подразделение / дочерние подразделения; статус владельца отличается от должности. |
| Вступление | На уровне организации настраиваются приглашения, заявки с одобрением или оба способа. |
| Проекты | Могут не иметь ответственного отдела, иметь один ответственный и несколько участвующих подразделений. |
| Комплектование команды | Руководитель проекта запрашивает людей у профильного отдела; руководитель отдела выбирает специалистов без обязательного участия HR как посредника. |
| Назначение в проект | Организация выбирает прямое назначение либо приглашение с подтверждением участника. |
| Постановка задачи | Настраивается прямое поручение от руководителя проекта либо маршрутизация через руководителя отдела. |
| Ответственность | У задачи один основной ответственный (после назначения) и может быть несколько соисполнителей. |
| Подзадачи | Простые чек-листы и полноценные подзадачи с преобразованием между типами. |
| Статусы | Стабильные системные этапы плюс пользовательские статусы, названия и правила перехода. |
| Проверка задач | Проверяет руководитель проекта, отдела или оба последовательно; маршрут настраивается. |
| Зависимости | Каждая зависимость либо предупреждает, либо строго блокирует начало выполнения. |
| Приоритеты | Настраиваемые на уровне организации названия, оформление и числовые ранги. |
| Уведомления | Централизованные правила на уровне организации. |
| Календарь | Единый просмотр сроков задач, встреч и мероприятий; три режима ответа на событие. |
| Аудит | История объектов в пределах прав, история направления у руководителей, полный аудит организации у уполномоченного администратора. |
| Конструктор | Обязательное ядро плюс подключаемые модули; выключение модуля не удаляет его данные. |
| Владение | Один владелец организации, несколько администраторов, безопасная передача владения. |
| Создание организации | Глобально настраивается: свободно, по разрешению либо через заявку. |
| Способы создания | С нуля, из шаблона и копированием конфигурации без рабочих данных (шаблоны и копирование — после MVP). |
| Интеграции | У каждой организации собственные ограниченные подключения под глобальной политикой платформы (расширенные внешние интеграции — после MVP). |

# 3. Функциональные требования MVP

## 3.1. Аккаунты и организации (FR-ORG)

**FR-ORG-01.** Регистрация, вход, выход и восстановление доступа; один глобальный аккаунт для нескольких организаций.

**FR-ORG-02.** Создание организации с нуля (название, краткое описание, логотип — необязателен), присвоение создателю статуса единственного владельца. Политика создания на платформе: открытая, только при наличии разрешения либо по заявке. Для начального развёртывания рекомендуем закрытый режим.

**FR-ORG-03.** Настройка статуса организации и её доступных модулей; локальные настройки не влияют на другие организации.

**FR-ORG-04.** Несколько администраторов с разными полномочиями; передача владения начинается владельцем и завершается явным принятием получателем. Передача регистрируется в аудите. Восстановление при потере доступа требует отдельной защищённой процедуры.

**FR-ORG-05.** Вступление в организацию через приглашение или заявку с одобрением — в соответствии с политикой организации. Участник может состоять в организации, не принадлежа ни одному подразделению.

## 3.2. Подразделения и участники (FR-DEP)

**FR-DEP-01.** Создание, переименование, перемещение и архивирование отделов, подотделов и иных организационных единиц. Количество уровней и их названия не зашиваются в код. Запрещены циклы при перемещении дерева.

**FR-DEP-02.** Пользователь может иметь несколько независимых членств в отделах. Разные роли в разных подразделениях допускаются. Исключение из отдела не исключает из организации.

**FR-DEP-03.** В списке родительского отдела показываются прямые участники и участники всех вложенных подразделений, каждый человек — единожды; указать путь членства, если их несколько. Это **только отображение**, не автоматическая выдача членства или прав.

**FR-DEP-04.** Настраиваемая видимость каталога: свой отдел, вся организация или разрешённые области. Пользователи вне текущего отдела в общем списке визуально приглушены, с текстовым пояснением; функции приглашения доступны только пользователям с соответствующим правом.

**FR-DEP-05.** Приглашение человека из организации в подразделение с отслеживанием состояния и защитой от повторных активных приглашений. Пользователь сохраняет другие членства. Добавление руководителем и принятие приглашения — разные операции.

## 3.3. Роли и права (FR-RBAC)

**FR-RBAC-01.** Должности/отображаемые названия отделены от технических разрешений. В комплекте идут стартовые шаблоны ролей, но названия «капитан», «PR», «секретарь» не используются как программные условия.

**FR-RBAC-02.** Назначение ролей в области организации, подразделения либо проекта. Отдельное свойство определяет, распространяется ли конкретное разрешение на дочерние подразделения.

**FR-RBAC-03.** Каждый запрос API проверяет членство организации, область полномочий и доступ к конкретному объекту; проверка только в интерфейсе недостаточна.

**FR-RBAC-04.** Для MVP допустим экран назначения разрешений по шаблонам и ключевым переключателям; полноценный визуальный редактор политик — последующий этап. При этом модель данных не должна блокировать дальнейшее развитие.

## 3.4. Проекты (FR-PRJ)

**FR-PRJ-01.** Проект создаётся в организации и содержит название, описание, состояние, руководителя и участников. Связь с отделами необязательна: отдельный ответственный отдел и несколько участвующих отделов.

**FR-PRJ-02.** Проектная команда формируется персонально. Принадлежность человека отделу сама по себе не добавляет его в проект и не открывает закрытые материалы.

**FR-PRJ-03.** Участник может находиться сразу в нескольких проектах. Руководитель проекта назначает проектные задачи в пределах разрешений, но не управляет членством человека в его исходном отделе.

**FR-PRJ-04.** Архивирование проекта не удаляет участников организации и не уничтожает связанные записи; активные процессы обрабатываются по правилам архивации.

## 3.5. Запросы людей в проект (FR-STAFF)

**FR-STAFF-01.** Руководитель проекта создаёт запрос профильному подразделению: нужное количество людей, назначение работ, желаемые сроки/период и, при необходимости, требования к навыкам.

**FR-STAFF-02.** Запрос адресуется обладателю права распределять работников выбранного отдела. HR не является универсальным посредником.

**FR-STAFF-03.** Руководитель подразделения видит доступную ему информацию о текущих поручениях людей, выбирает нужных специалистов и выполняет запрос полностью или частично, с возможностью сообщить об отсутствии доступных людей.

**FR-STAFF-04.** По политике организации выбранные сотрудники либо сразу включаются в проект, либо получают приглашение. Проектный руководитель уведомляется о результате без обязательного утверждения каждой кандидатуры.

**FR-STAFF-05.** Вся цепочка действий по запросу и распределению фиксируется в истории. Членство в исходном отделе не меняется.

## 3.6. Задачи и процессы (FR-TASK)

**FR-TASK-01.** Задача принадлежит организации. Название обязательно; описание, проект, отдел, исполнитель, сроки, приоритет — опциональны, когда это допустимо бизнес-правилами. Авторы и даты создания заполняются автоматически.

**FR-TASK-02.** После распределения у задачи один основной ответственный; допускаются несколько соисполнителей. До назначения ответственный может отсутствовать.

**FR-TASK-03.** Режим постановки задач настраивается: прямое назначение допустимым руководителем проекта либо передача через руководителя профильного подразделения. При маршрутизации создаётся **одна** задача в состоянии ожидания распределения, а не дубликаты.

**FR-TASK-04.** Полноценные подзадачи имеют собственные статусы, сроки, ответственных, соисполнителей и историю. Чек-листы содержат простые пункты. Поддерживается преобразование чек-листа в подзадачу и обратное — с проверкой потерь данных и подтверждением пользователя. Запрещены циклы и вложение задачи в себя.

**FR-TASK-05.** Системные этапы: ожидание, в работе, проверка, завершено, отменено. Пользовательские статусы привязаны к системному этапу; их наименования, ранги и разрешённые переходы настраиваются в организации. Блокировка/препятствие — дополнительный признак, не уничтожающий текущий этап.

**FR-TASK-06.** Маршрут проверки результата: один профильный проверяющий проекта или отдела либо оба последовательно. Возврат сопровождается замечанием; предшествующие результаты проверок сохраняются. Задача закрывается после обязательных согласований.

**FR-TASK-07.** Для задачи хранятся плановая дата начала, дедлайн и фактическое завершение; даты могут отсутствовать. Изменение сроков фиксируется в аудите.

**FR-TASK-08.** Поддерживаются связи зависимости «B зависит от A»: информационная или строгая. Строгая блокирует перевод в работу при незавершённом предшественнике, но не блокирует просмотр/комментарии. Отмена предшественника не означает выполнения. Запрещены циклические зависимости.

**FR-TASK-09.** Приоритеты создаются на уровне организации и имеют редактируемые названия и числовой порядок; права редактирования ограничены.

**FR-TASK-10.** Участнику доступен список «Мои задачи»: основная ответственность, соисполнение, назначенные подзадачи; фильтры по дедлайну, статусу, приоритету, проекту и отделу.

## 3.7. Календарь, встречи, мероприятия (FR-CAL)

**FR-CAL-01.** Общая календарная система показывает дедлайны задач и отдельные календарные события без дублирования задачи как второго объекта. Представления: день, неделя, месяц.

**FR-CAL-02.** Событие содержит название, тип, начало, окончание, организатора, место/ссылку, описание, связь с организацией и опционально с отделом или проектом; поддерживаются повторяющиеся события.

**FR-CAL-03.** Приглашение адресуется всей организации, нескольким отделам, проектным командам и отдельным участникам с дедупликацией по человеку. Подразделения могут включать дочерние при выборе организатора.

**FR-CAL-04.** Видимость события и приглашение — независимые правила. Возможны три режима: информационное объявление (ответ не нужен); приглашение с ответом; приглашение с обязательным ответом. Отказ «Не смогу» считается ответом, а не нарушением обязательного присутствия.

**FR-CAL-05.** Статусы ответа: приму участие / возможно / не смогу / не ответил. Организатор видит итоги доступного ему события. Доступ к содержимому закрытых событий проверяется на сервере.

**FR-CAL-06.** Календарь фильтруется по областям доступа, проектам, отделам, типам и участникам. Событие человека из нескольких групп не дублируется.

**FR-CAL-07.** Время хранится с часовым поясом; по умолчанию для пилота — Asia/Almaty, с возможностью настроек организации. Редактирование серии повторов должно различать отдельное вхождение и всю серию (конкретный UX уточняется на этапе интерфейсов).

## 3.8. Уведомления и аудит (FR-NOT / FR-AUD)

**FR-NOT-01.** Внутренний центр уведомлений MVP: новое назначение, приглашение, запрос сотрудников, проверка, комментарий/упоминание, приближение дедлайна, просрочка, изменение важных дат, ответ на приглашение.

**FR-NOT-02.** Администрация организации централизованно задаёт, какие рабочие события уведомляют и по каким интервалам. Пользователь может отметить прочитанным, но не меняет обязательные правила организации. Статус «прочитано» не закрывает исходный запрос или задачу.

**FR-NOT-03.** Напоминания рассчитываются с учётом актуального дедлайна: изменение времени отменяет/пересчитывает прежние запланированные оповещения. Предусмотреть отсутствие дублей при повторной обработке.

**FR-AUD-01.** Записывать кто, когда, какой объект и какое значимое поле изменил; где допустимо — старое/новое значение. Раздельно история объекта и административный аудит.

**FR-AUD-02.** Участник видит историю доступного объекта; руководитель — историю объектов в своей компетенции; полный аудит организации — только по отдельному разрешению. Важные события аудита не редактируются из интерфейса.

## 3.9. Главная панель и включение модулей (FR-DASH / FR-MOD)

**FR-DASH-01.** Главная страница MVP отображает «Мои задачи», активные проекты, ближайшие дедлайны, события и задачи, требующие внимания; небольшие общие счётчики строятся только по разрешённым данным.

**FR-DASH-02.** Полноценный конструктор дашбордов с произвольными виджетами **не входит в MVP**.

**FR-MOD-01.** Ядро (пользователи, организации, отделы, членства, роли, права, конфигурация, аудит) всегда включено. Организация управляет доступностью подключаемых модулей.

**FR-MOD-02.** Отключение модуля не удаляет его записи. Запросы к выключенному модулю отклоняются и на фронтенде, и сервером. Учитывать зависимости модулей, показывать администратору последствия переключения.

**Критерий пилотного запуска:** реальная команда может пройти непрерывный путь «создание Enactus → отделы/участники → проект → запрос людей → назначение → задача → выполнение/проверка → календарное событие», не прибегая к ручной правке БД и не затрагивая другую организацию.

# 5. Техническая архитектура

**Согласованный стек:** Python + Django + Django Ninja + PostgreSQL. Frontend — Django Templates / HTML5, CSS3, обычный JavaScript с ES Modules; без обязательного React. Архитектура — модульный монолит. REST API с пространством `/api/v1/` обслуживает и веб-интерфейс, и будущие клиенты.

**Рекомендуемая организация кода (не буквальное дерево проекта):** `accounts`, `organizations`, `departments`, `permissions`, `projects`, `staffing`, `tasks`, `calendar`, `notifications`, `audit`, `dashboard`, `integrations` (позже). Разделить код маршрутов/API, бизнес-сервисы, проверки политик, модели и представления.

**Авторизация для MVP:** серверная сессия Django с HttpOnly/Secure cookies и CSRF-защитой для одноимённого веб-сайта; для внешних сервисов позже отдельные отзывные токены с scopes. Не хранить секреты авторизации в LocalStorage. Предусмотреть аутентификацию, авторизацию и проверку доступности модулей как три отдельные проверки.

**Многопользовательская изоляция:** записи организации имеют явную принадлежность организации. Все выборки и изменения ограничены идентификатором выбранной организации, членством и объектными полномочиями. Для связанных записей запрещены связи «проект из организации A → участник из B». Для аудита — та же изоляция.

**Асинхронные процессы:** отправка уведомлений и обработка расписания событий должны быть устойчивы к повторным запускам. Конкретная очередь задач (например, Celery + Redis) — рекомендация для реализации, а не уже утверждённая инфраструктурная зависимость.

Ниже **концептуальные сущности**, а не окончательная SQL-схема. Поля, ограничения и индексы будут детализированы на этапе ER-модели.

# 7. Проектируемый REST API

Все маршруты ниже — **предварительный контракт**; имена и payload будут утверждаться после ER-модели.

| Метод | Путь | Назначение |
|---|---|---|
| GET/POST | `/api/v1/organizations/` | Список разрешённых организаций / создание |
| GET/PATCH | `/api/v1/organizations/{org_id}/` | Сведения и настройки организации |
| GET/POST | `/api/v1/organizations/{org_id}/departments/` | Дерево / создание подразделения |
| GET/POST | `/api/v1/organizations/{org_id}/members/` | Участники, приглашения (отдельными действиями) |
| GET/POST | `/api/v1/organizations/{org_id}/projects/` | Проекты организации |
| GET/POST | `/api/v1/organizations/{org_id}/staffing-requests/` | Запросы специалистов |
| POST | `/api/v1/organizations/{org_id}/staffing-requests/{id}/allocate/` | Выделение людей отделом |
| GET/POST | `/api/v1/organizations/{org_id}/tasks/` | Поиск и создание задач |
| PATCH | `/api/v1/organizations/{org_id}/tasks/{id}/` | Изменение полей задачи |
| POST | `/api/v1/organizations/{org_id}/tasks/{id}/transition/` | Разрешённый переход статуса |
| POST | `/api/v1/organizations/{org_id}/tasks/{id}/review/` | Принятие или возврат результата |
| GET/POST | `/api/v1/organizations/{org_id}/events/` | Календарные события |
| POST | `/api/v1/organizations/{org_id}/events/{id}/rsvp/` | Ответ на приглашение |
| GET | `/api/v1/organizations/{org_id}/dashboard/` | Персонализированная по правам сводка |
| GET | `/api/v1/organizations/{org_id}/notifications/` | Уведомления текущего участника |
| GET | `/api/v1/organizations/{org_id}/audit/` | Системный аудит (по особому праву) |

**Требования к API:** пагинация, фильтры, безопасная сортировка, понятные коды ошибок, идемпотентность чувствительных повторных действий, OpenAPI-документация, версионирование, валидирование входных данных, контроль прав на каждый объект, защита от массовых назначений/рассылок.

# 8. Интерфейсы и навигация

**Глобальный уровень:** вход/регистрация; выбор организаций; создание рабочей области; личный профиль; системные сообщения.

**Внутри организации:** главная панель; структура подразделений; участники; проекты; запросы участников; задачи («Мои», все доступные, Kanban/список); календарь; уведомления; настройки ролей и модулей; ограниченный журнал действий.

**Общие UX-правила:** адаптивная верстка для компьютера и телефона, клавиатурная доступность, текстовые метки статусов (не полагаться только на цвет), единые модальные окна/формы, понятные сообщения об ошибках, подтверждение опасных действий, поиск и фильтры. Первая локаль — русский; архитектура строк должна позволять добавить казахский и английский.

**Фронтенд без фреймворка:** ES-модули для API-клиента, общих компонентов и логики страниц; не собирать всю логику в один `script.js`. Предпочтительно избегать ручного небезопасного `innerHTML` для пользовательских строк, использовать безопасный вывод и серверную валидацию.

# 9. Нефункциональные требования и безопасность

- HTTPS в рабочем окружении; Secure/HttpOnly/SameSite cookies; CSRF-защита; хеширование паролей штатными средствами Django.
- Все операции над организационными данными и разрешениями проверяются на сервере; не доверять `organization_id`, пришедшему от клиента, без проверки членства.
- Контроль конкурентных изменений назначений и утверждений; транзакции для критических операций.
- Ограничения частоты для входа, заявок, приглашений и массовых действий; логирование ошибок без утечки секретов.
- Резервное копирование PostgreSQL, документированная процедура восстановления, разделение dev/test/prod окружений.
- План миграций БД и тестирования. Минимум: юнит-тесты прав и бизнес-сервисов, API-тесты с несколькими организациями, интеграционные сценарии пилота.
- Правила обработки персональных данных и сроки хранения уточняются перед внешним развёртыванием; не собирать лишние поля профиля.
- Временные метки — timezone-aware; корректная локальная выдача пользователю.
- Никаких обещаний «абсолютной безопасности»: аудит не заменяет ограничения доступа, резервные копии и процедуры администрирования.

| 5. Календарь | Виды день/неделя/месяц, события, приглашения, RSVP, повторы, сроки задач | Собрание можно назначить команде и получить ответы |
| 6. Сервисные модули | Уведомления, аудит, сводная панель, управление включением модулей | Полностью проходит набор приёмочных сценариев |
| 7. Пилот | Перенос актуального состава и проектов Enactus, тестирование прав, исправления | Команда использует систему для действительных поручений |

**Порядок этапов — рекомендуемый, без фиксированных календарных обещаний.** Небольшой инкремент доводим до работающего состояния и тестов прежде, чем расширять следующий.

# 13. Подробные правила реализации и граничные случаи

Это уточнение не заменяет функциональные требования 3.1–3.9, а делает их проверяемыми для Codex.

## 13.1. Владение, членство и изоляция

- Глобальная учётная запись одна; членство в нескольких организациях независимо. Системный суперпользователь Django **не эквивалентен** владельцу каждой организации, хотя в локальной dev-среде может администрировать Django Admin.
- Владелец организации ровно один; при создании автоматически становится активным членом. Предусмотреть администратора/нескольких администраторов в дополнение к владельцу. Права администраторов — управляемые, не безусловные.
- Передача владения: отдельный запрос, явное принятие новым владельцем, атомарная замена собственника, аудит; до принятия старый остаётся владельцем. Нельзя передать владение участнику чужого tenant без явного корректного включения в целевую организацию.
- Политика создания организаций на уровне платформы: открытая / по разрешению / по одобряемой заявке. Первоначальное развёртывание — закрытое. В MVP создание только с нуля; шаблоны и копирование конфигурации позже.
- Организация управляет вступлением: приглашение, заявка с одобрением или оба. Вступивший может не состоять ни в одном отделе. Прекращение членства не стирает аудит/историческое авторство задач, но отзывает текущий доступ; открытые задачи отмечаются для переназначения.
- Все queryset и сервисы, получающие `org_id`, `department_id`, `project_id`, `task_id`, проверяют на сервере связность и права. Проверка только по совпадению ID не является проверкой доступа. Для недоступных ресурсов предпочитать нераскрывающий `404` там, где это уместно.
- На всех назначениях, связях и переносах запрещены ссылки на объекты другой организации. Хранение `organization_id` в каждой доменной сущности с проверкой консистентности связей.

## 13.2. Иерархия и каталог людей

- Произвольное дерево через `parent_id` с запретом собственного родителя, замыкания дерева и связей между организациями. Перенос отдела сохраняет людей и историю; архивирование не равнозначно удалению.
- Прямые членства и отображаемое охватывающее членство **разные понятия**. Участник IT виден в Project, но не получает автоматически прямую запись `DepartmentMembership(Project)` и руководящие права Project.
- Родительский список показывает уникальных людей из всех потомков, рядом выводит все фактические пути членства: `Project`, `Project / IT` и т. п.; один пользователь — одна карточка.
- В каталоге организации: сотрудники выбранного отдела/потомков обычным видом, другие доступные сотрудники той же организации приглушённо + текстовый статус. Это **не средство защиты**; запрет видимости/действия производится серверными правами. Можно отправить приглашение в отдел, если есть право; двойные активные приглашения предотвращать.
- Названия и типы подразделений настраиваются (отдел, сектор, комиссия и т. п.). Плоская структура — частный случай дерева.
- Для больших деревьев допускается оптимизация обхода рекурсивным SQL CTE либо предвычисленным представлением; на начальном этапе допустим простой проверенный обход дерева без преждевременной оптимизации.

## 13.3. Роли, полномочия и наследование

- Разделить `position_title` (человекочитаемая должность) и `Permission` (набор конкретных действий). Никакого `if role_name == 'captain'` в бизнес-логике.
- Область назначения роли: организация / конкретный отдел / конкретный проект. Полномочия отдела наследуются на дочерние только при явном флаге `include_descendants` для нужных действий; не наследовать доступ к конфиденциальным объектам автоматически.
- Нужен единый `can(user, action, object, org)` либо эквивалентный policy/service-layer; использовать и в HTML views, и в Ninja API, и в фоновых задачах. По умолчанию запрет.
- Модель ролей может поддерживать несколько назначений одному человеку, в том числе в разных отделах, и разные роли в разных проектах.
- Минимальные разрешения: организации (read/update/manage_members/manage_roles/transfer_ownership), отделы (read/create/update/manage_members/allocate), проекты (read/create/update/manage_members), задачи (read/create/assign/update/transition/review), календарь (read/create/update/invite), уведомления (read_own/manage_rules), аудит (read_scoped/read_all), модули (configure). Точный naming scheme определить один раз и документировать.

## 13.4. Проекты и запрос специалистов

- Проект всегда принадлежит организации, может быть независимым, иметь **не более одного ответственного отдела** и любое количество участвующих. Проектная команда хранится отдельными персональными членствами и ролями.
- Проектный руководитель отправляет заявку: целевой отдел, количество людей, ожидаемая работа, желаемый период/срок, требования. Руководитель профильного отдела, имеющий `allocate`, сам выбирает специалистов, в том числе назначает меньше запрошенного количества или предлагает другую дату. HR **не посредничает** в запросах, адресованных PR/Event/Project.
- Режим вступления по правилу организации: прямое назначение либо приглашение и подтверждение участника. Если приглашение отклонено, штатная заявка не должна считаться полностью закрытой.
- Назначение в проект сохраняет прежние членства во всех отделах. У одного человека несколько проектов. Руководитель проекта может видеть релевантную нагрузку выделенного работника, но не скрытые подробности чужих задач.
- История запроса: создан → рассматривается → частично выделено / выполнено / отказано / отменено; какие люди направлены, кто и когда. Статусы согласовать с реализацией, не превращать в «просто комментарий к проекту».

## 13.5. Задачи — неизменяемые инварианты процесса

- У задачи всегда есть организация, автор, заголовок и системный этап; связь с проектом и отделом опциональна. Основной ответственный может быть пуст до назначения, после назначения — максимум один. Соисполнителей может быть много.
- При маршруте «через подразделение» создаётся **один** объект задачи, ожидающий распределения; руководитель отдела назначает главного исполнителя. При прямом маршруте уполномоченный руководитель проекта назначает сразу.
- Системные состояния, доступные бизнес-логике: `PENDING`, `IN_PROGRESS`, `REVIEW`, `COMPLETED`, `CANCELLED`. Пользовательские статусы в организации отображаются поверх системных и имеют разрешённые переходы. Дополнительный флаг блокировки не заменяет системный этап.
- Проверка результата: проектный руководитель, руководитель отдела либо оба последовательно; возвращение с замечанием; хранение решений по каждому этапу; нельзя перейти к `COMPLETED` с незавершённой обязательной проверкой.
- Чек-листы (простые отметки) и подзадачи (полноценные объекты `Task` с `parent_id`). Конвертация пункт → задача допустима; обратная — только с предупреждением, если есть сроки, исполнители, комментарии и история; данные не удалять молча.
- Зависимость «B ждёт A» хранит тип `warning`/`blocking`. Блокирующая — сервер запрещает **начать** выполнение, пока A не завершена; просматривать/планировать/комментировать B можно. Отмена A не означает завершение A. Запрет циклов графа зависимостей и дерева задач.
- Сроки: `planned_start_at`, `due_at`, `completed_at`; временные значения timezone-aware; дедлайны необязательны. При конфликте срока подзадачи с родительской показывать предупреждение, не переносить автоматически.
- Уровни приоритетов организация создаёт сама с числовым рангом и представлением, по умолчанию есть разумные стартовые значения. Право изменять приоритет регулируется.
- Комментарии и история доступных задач; не смешивать «прочитано уведомление» и «выполнена задача».

## 13.6. Календарь — полный функционал MVP

- Визуализация **день / неделя / месяц**. В одном источнике: отображение дедлайнов Task и самостоятельных Event; **не клонировать Task в Event**.
- Создание, изменение, отмена события: название, тип (встреча, собрание, мероприятие и расширяемые типы), начало/окончание, таймзона, описание, место либо URL, организатор, связанный отдел и/или проект, видимость.
- Приглашённые: организация, один/несколько отделов (по выбору с потомками), одна/несколько проектных команд, выбранные пользователи. При пересечении групп — один `EventInvitee` на человека. Сохранять источник приглашения, если нужно объяснить почему пользователь приглашён.
- Режим события (строго три): `ANNOUNCEMENT` (ответа нет), `RSVP_OPTIONAL` (ответ возможен), `RSVP_REQUIRED` (обязательно **дать ответ**, но ответ «не смогу» допустим). Не превращать `required` в принудительное участие. Ответы `YES`, `MAYBE`, `NO`, `PENDING`.
- Видимость события и факт приглашения независимы. Без приглашения пользователь может видеть общее мероприятие, если разрешено; закрытое собрание не должно раскрывать детали.
- Поддержка повторяющихся событий: правила повтора, корректная работа с часовыми поясами и исключения при переносе/отмене одной встречи. Изменение «один экземпляр» и «всю серию» оформляется явно.
- Обновление дедлайна задачи немедленно обновляет его отображение на календаре без создания новой записи события. Фильтры по отделам, проектам, типам и личному участию.
- Внешняя синхронизация с Google Calendar в MVP **не входит**.

## 13.7. Уведомления, аудит и главная панель

- Внутренний inbox уведомлений доступен из любого раздела. Создание задачи, приглашение, запрос ресурсов, назначение и проверка, приближение дедлайна, изменение срока, просрочка, RSVP, упоминание в комментарии — уведомления по настройкам организации.
- Управление правилами уведомлений централизовано администрацией организации. В MVP достаточно внутреннего центра, внешние email/Telegram — позже. Персональные каналы не подключать без согласия владельца аккаунта.
- Источник уведомления — событие, а не просто текст. Доставка и напоминания идемпотентны, дедлайн при переносе пересчитывает расписание. Отметка о прочтении не изменяет бизнес-статус объекта.
- Аудит: actor, organization, действие, объект, время, допустимые значения before/after без секретов; история отдельного объекта; руководители видят только свой scope, доступ ко всему аудиту — отдельное полномочие.
- MVP-dashboard: «мои задачи», ближайшие сроки, приглашения/события, активные проекты, задачи на проверку, заблокированные/просроченные. Данные только разрешённые. Конструктор виджетов — после MVP.

- **Calendar:** модель событий/RSVP/повторы вместе с согласованным API; координирует изменения API со Backend и UI с Frontend.
- **Coordinator:** межмодульные контракты, интеграция, ревью diff, общие тесты, оформление статуса и merge.

При одновременном редактировании избегать общих файлов, например `config/settings.py`, `config/urls.py`, `AGENTS.md`, `compose.yaml`. Главный агент владеет ими либо назначает владельца на конкретный этап.

# 15. Концептуальная модель данных и ограничения

Все сущности проектируются **с чистого листа**. На этапе 1 необходимо принять решение о модели пользователя ДО первой миграции. Рекомендуется собственный `User(AbstractUser)` или `User(AbstractBaseUser)` только при реальной необходимости; простой `AbstractUser` даёт стабильную возможность расширять профиль без болезненной замены `auth.User` в будущем. Выбор зафиксировать в `docs/DECISIONS.md`, выставить `AUTH_USER_MODEL` до применения миграций. Глобальный профиль и организационное членство — разные объекты.

| Сущность | Ключевые поля/связи | Инвариант |
|---|---|---|
| `User` | идентификатор, логин/email, пароль-хеш, активность | Один аккаунт для всех организаций |
| `Organization` | name, owner, settings, state | Ровно один владелец |
| `OrganizationMembership` | org, user, joined_at, state | Одна активная/логическая запись на `(org, user)` |
| `Department` | org, parent (nullable), name, archive | Родитель той же org, дерево без циклов |
| `DepartmentMembership` | department, org_membership, role assignments | Участник org не обязан состоять в одном основном отделе |
| `Role`/`Permission`/`RoleAssignment` | org, permission_code, scope, include_descendants | Scope проверяется в сервисах/queries, не только в UI |
| `Project` | org, title, responsible_dept(nullable) | Один проект принадлежит только одной org |
| `ProjectDepartmentLink` | project, department, participation_type | Много участвующих отделов, максимум один ответственный |
| `ProjectMembership` | project, org_membership, project_role | Никаких cross-org связей |
| `StaffingRequest` | project, target_department, count, details, state | Целевой отдел выбирает специалистов |
| `StaffingAllocation` | request, user, assignment_state | Назначенные люди остаются в исходном отделе |
| `Task` | org, project?, department?, parent?, title, due?, state | Нет циклов, единственная org |
| `TaskAssignee` | task, user, kind(owner/collaborator) | Не более одного главного исполнителя |
| `TaskStatus`/`TaskTransition` | org, system_stage, user_label, rank | Системный этап фиксирован, подписи настраиваются |
| `TaskReviewStep` | task, assigned_reviewer, sequence, decision | Закрытие только после обязательных проверок |
| `TaskDependency` | predecessor, successor, mode | Циклы запрещены, cross-org связи запрещены |
| `ChecklistItem` | task, text, done, order | Сам по себе не Task |
| `CalendarEvent` | org, start/end tz-aware, type, visibility, repeat | Время корректно с учётом TZ |
| `EventInvitation`/`EventRSVP` | event, user, source groups, response | Приглашённый пользователь уникален в событии |
| `Notification`/`AuditEvent` | org, actor/recipient, ref, timestamp | Отделение источника события и канала; приватность |
| `OrganizationModule` | org, module_code, enabled | Выключение не удаляет данные |

**Обязательные ограничения:** FK и DB-unique, валидация межорганизационных связей, роль/полномочие с областью действия, запрет циклов (дерево отделов/подзадач/зависимостей), concurrency-safe операции согласования, единый источник системного статуса. Там, где простая `CHECK`-проверка в PostgreSQL не способна валидировать FK-связанную org, использовать транзакционные сервисы и тесты; в интерфейсе Django Admin также валидировать вход.

**Не создавать** заранее модели протоколов, отчётов, файловых версий и внешних интеграций ради красивой ERD — они появятся после MVP.

# 16. Контракт API с нуля

1. Django Ninja, `/api/v1/`, OpenAPI. Для каждой операции обязательны request/response schema, авторизация, object-level permission, tenant filter и негативный тест чужой организации.
2. Один и тот же REST API используется серверными страницами/JS и будущими клиентами; не делать два несовместимых бэкенда.
3. Сессионная аутентификация для браузера; безопасная CSRF-обработка операций записи. Внешние токены и OAuth — не в MVP.
4. `GET` безопасен для чтения и не меняет данные, `POST/PATCH/DELETE` требуют корректной проверки прав; для повторяемых критических операций нужна идемпотентность.
5. Не раскрывать закрытые ресурсы через последовательное перебирание ID; HTTP 403/404 выбираются с учётом скрытия существования и отображения корректной ошибки.
6. Предусмотреть пагинацию, поиск/фильтры, валидацию, логирование технических ошибок без секретов.
7. Согласовать схемы API между backend/frontend агентами до параллельного кодирования и фиксировать их в `docs/API.md`.

Примеры возможных маршрутов — в разделе 7; на первом этапе не реализовывать все эндпоинты разом.

# 17. UI, навигация, доступность

Главные страницы MVP: логин и регистрация, выбор организации, оргструктура, каталог людей и приглашений, проекты, запросы людей, задачи и канбан, календарь (день/неделя/месяц), центр уведомлений, панель, настройки ролей/модулей.

**Frontend:** Django Templates + чистые HTML/CSS/JavaScript (ES Modules), без React, Vue, Next.js и других SPA-фреймворков. Компоненты реализуются модульно. Не генерировать пользовательские строки через unsafe `innerHTML` без очистки; использовать `textContent` и шаблонизатор с escaping.

**UX:** адаптивность desktop/mobile, клавиатурная навигация, доступность контрастов, фокусные состояния, семантика и aria для интерактивных кнопок, сообщения об ошибках, сохранение фильтров на время сессии (без секретов), русская локаль с возможностью расширения на kk/en.

**Calendar UX:** создание/редактирование встреч и мероприятий, выбор приглашённых (отделы, проекты, лица), три режима ответа, визуальное отличие дедлайна от встречи, редактирование повторов и исключений. Backend гарантирует пересчёт и дедупликацию приглашений.

# 18. Среда с нуля: Docker, настройки, секреты, запуск

## 18.1. Новый dev-контур

- Система разработчика: Arch Linux. Codex создаёт `Dockerfile`, `compose.yaml`, `.env.example`, `.gitignore`, README с точной инструкцией запуска.

Пример: `COMPOSE_PROJECT_NAME=enactus_os_next`, `POSTGRES_DB=enactus_os_next`, DB external port только `127.0.0.1:55433` если он свободен, web port `127.0.0.1:8002` если свободен. Важно: не подключать локальные данные прежних проектов.
- Секреты только в `.env` или другом безопасном секретном хранилище. В Git коммитить только `.env.example` без чувствительных значений. `DJANGO_SECRET_KEY` и пароль PostgreSQL должны быть случайными и разными. **Не генерировать `.env` со слабым фиксированным паролем.** Codex может создать секреты прямо в `.env` нового проекта и не показывать их в ответе.
- Избегать зависимости от локального Python 3.14.6: для контейнера зафиксировать проверенную совместимую версию Python, например 3.12 или 3.13, и совместимую Django LTS (5.2 при согласованной ветке). Версии библиотек закреплять/обновлять с тестами.
- При начале разработки: сначала проверить, существует ли новая папка; если существует и содержит файлы, **не перезаписывать** без сверки. Старые папки `enactusos` и `enactus-os` не трогать.

Пример первичного запуска для Codex после создания файлов:

```bash

docker compose up --build -d

```

Конкретную команду миграций (`docker compose exec web python manage.py migrate`, или отдельный migrate task) согласовать с выбранной схемой запуска. Не делать `runserver` сервисом для production.

## 18.2. Защита данных и копий

- Для нового проекта можно начинать с пустой базы. Однако после появления данных нельзя удалять volume/использовать `down -v` без отдельного явного разрешения и backup.
- При создании DevOps обязан документировать как получить и восстановить дамп (`pg_dump`/`pg_restore`) в **новой временной БД**, не старой базе.
- Пароль PostgreSQL фиксируется при инициализации volume: изменение `.env` не переназначает его внутри существующей БД.
- Отключить внешнюю публикацию БД. При публикации проекта использовать HTTPS, проверку CORS/CSRF, корректные ALLOWED_HOSTS и обратный прокси.

## 18.3. Отдельные среды

- `dev`: локальный compose, тестовые данные, DEBUG=True, только loopback.
- `test`: тестовая БД/отдельный контур; миграции, unit и API tests; при интеграционных тестах не пересоздавать пользовательскую БД.
- `prod` (после прохождения приемки): DEBUG=False, HTTPS, закреплённые версии, backup, health monitoring, секреты вне VCS. Нет открытого `runserver`.

# 19. Тестирование и критерии приёмки

## 19.1. Базовые тесты нового проекта

В новом репозитории **нет заранее готовых пяти тестов**; нельзя ссылаться на прошлые результаты. С первого рабочего инкремента создать новые тесты и постепенно покрыть:

- изоляцию организаций (чтение, запись, API по чужому org id);
- владельца, администраторов, смену ролей, прямых и вложенных участников;
- запрет циклов отделов/подзадач/зависимостей и cross-org связей;
- запрос кадров проекта напрямую профильному отделу; назначение руководителем отдела и режим приглашения;
- задачу с основным/соисполнителями; отложенное распределение через отдел; согласование; пользовательские статусы/переходы;
- дедлайны задач в календаре без дублирования сущности; повторы и исключения встреч; RSVP в трёх режимах;
- централизованные уведомления, идемпотентность, приватность аудита;
- модульные флаги не удаляют данные и действуют в API;
- безопасную обработку HTML/JS, CSRF, запреты IDOR и эскалации полномочий.

## 19.2. Сквозная приёмка

Сценарии **AT-01–AT-12** из раздела 4 и дополнительные **AT-13–AT-18** ниже должны проходить на новой платформе:

**AT-13.** Публичный интерфейс (не Django Admin) отображает дерево отделов и уникальных участников с путями членства, недоступная организация отклоняется.

**AT-14.** Новый дедлайн/перенос срока задачи отражается в календаре без создания Event-дубликата.

**AT-15.** Повторяющееся событие можно изменить для одного экземпляра, не меняя всю серию.

**AT-16.** Невозможна выдача/назначение участников из другого org; злоумышленнику не раскрывается закрытый состав команды.

**AT-17.** Новую организацию и отдел можно создать в пользовательском интерфейсе; обычный участник не может обойти права через API.

**AT-18.** После перезапуска `web/db` сохранённые данные остаются, миграции идемпотентно применяются к существующей новой базе без обнуления.

## 19.3. Definition of Done каждой задачи субагента

1. Чёткий scope + список принадлежащих файлов + контракт API/data, если затрагивается интеграция.
2. Рабочая реализация, без секретов или внешних пользовательских данных в коде.
3. Положительные и отрицательные тесты, включая cross-tenant, если это организационные данные.
4. Запущены релевантные команды и показан фактический output; не «предположительно тестируется».
5. Ревью независимым QA/Security-субагентом при изменении прав, авторизации, sensitive data, RSVP, миграций.
6. Главный агент прогнал интеграционные проверки, сверил контракты и собрал итоговый diff.
7. Документация обновлена (`docs/API.md`, `docs/ERD.md`, `docs/DECISIONS.md`, `docs/STATUS.md` по ситуации).
8. Пользователь получает краткий отчёт «что готово / какие файлы / какие тесты / что осталось», затем контрольная точка.
