# API

Для вступления действуют почасовые лимиты на организацию и аккаунт. Один управляющий может создать до 20 приглашений, один заявитель — до 5 заявок. При превышении сервер возвращает HTTP 429.

| Метод | Маршрут | Доступ и ответ |
|---|---|---|
| GET | `/api/v1/health/` | Публичный. HTTP 200 и JSON `{"status":"ok"}`. Проверяет HTTP-процесс, доступность БД проверяет Compose. |
| GET | `/api/v1/openapi.json` | Схема API в режиме разработки. |
| GET | `/api/v1/docs` | Swagger UI в режиме разработки. |

Вход через Django `GET/POST /accounts/login/`, выход через `POST /accounts/logout/`. Формы защищены CSRF. Главная страница `/` доступна после входа.

## Организации

| Метод | Маршрут | Успешный ответ |
|---|---|---|
| GET | `/api/v1/organizations/` | HTTP 200, массив доступных организаций в порядке возрастания идентификатора. |
| POST | `/api/v1/organizations/` | HTTP 201, созданная организация. Создателю присваиваются владение и активное членство. |
| GET | `/api/v1/organizations/{id}/` | HTTP 200, организация с указанным целочисленным идентификатором. |

Объект организации содержит целочисленный `id`, строку `name` и время создания `created_at` в ISO 8601. Для создания передайте JSON вида `{"name":"Enactus Toraighyrov"}`. Пробелы по краям удаляются, длина названия должна составлять от 1 до 200 символов. Нулевой символ NUL отклоняется. Ошибка проверки тела запроса возвращает HTTP 422.

Для чтения требуются сессия Django и активное членство. Запрос конкретной организации без активного членства возвращает HTTP 404, как и запрос отсутствующего идентификатора. Правило действует и для суперпользователя.

Для создания требуются сессия Django, CSRF-токен в заголовке `X-CSRFToken` и разрешение `organizations.add_organization`. Анонимный GET и анонимный POST с действительным CSRF-токеном возвращают HTTP 401. POST без действительного CSRF-токена или без разрешения на создание возвращает HTTP 403.

Веб-страницы `/organizations/` и `/organizations/{id}/` используют те же правила чтения. Анонимного посетителя перенаправляют на страницу входа.

## Веб-страницы вступления

| Маршрут | Доступ и действия |
|---|---|
| `/organizations/{id}/manage/` | Владелец или активный участник с правом управления просматривает состав, создаёт и отзывает приглашения, одобряет и отклоняет заявки. Изменение правил вступления и делегирование доступны владельцу с активным членством. |
| `/organizations/invitations/` | Авторизованный получатель видит свои действующие приглашения. Ответить можно из списка либо по ссылке с токеном во фрагменте URL. |
| `/organizations/join/{code}/` | Авторизованный пользователь с действительной подписанной ссылкой может подать заявку, пока организация принимает заявки. |

HTML-формы отправляют изменения методом POST с CSRF-токеном. Страница управления отвечает HTTP 404 при отсутствии активного членства и HTTP 403 при отсутствии права управления. Недействительная ссылка на подачу заявки и выключенный режим заявок возвращают HTTP 404. Повторный ответ или другой конфликт состояния возвращает HTTP 409.

## API вступления

Все маршруты в таблице относительны к `/api/v1/organizations`. Требуется сессия Django, а для POST, PATCH и DELETE также заголовок `X-CSRFToken`.

| Метод | Маршрут | Тело запроса | Успешный ответ |
|---|---|---|---|
| GET | `/{org_id}/members/` | — | HTTP 200, сводка управления участниками. |
| PATCH | `/{org_id}/join-policy/` | `{"policy":"invites"}`. Допустимы также `requests` и `both`. | HTTP 204. |
| PATCH | `/{org_id}/members/{membership_id}/` | `{"enabled":true}` | HTTP 204. |
| POST | `/{org_id}/invitations/` | `{"username":"username"}` | HTTP 201, приглашение с полем `token`. |
| DELETE | `/{org_id}/invitations/{invitation_id}/` | — | HTTP 204. |
| GET | `/invitations/` | — | HTTP 200, массив действующих приглашений текущего пользователя с полем `organization_name`. |
| POST | `/invitations/respond/` | `{"invitation_id":123,"decision":"accept"}`. Вместо `invitation_id` можно передать `token`. Для отказа укажите `"decision":"decline"`. | HTTP 200, приглашение с итоговым статусом. |
| POST | `/join/{code}/` | — | HTTP 201, заявка. |
| POST | `/{org_id}/join-requests/{request_id}/review/` | `{"approve":true}`. Для отказа передайте `false`. | HTTP 200, заявка с итоговым статусом. |

Сводка управления содержит `join_policy`, `join_code`, `members`, `invitations` и `join_requests`. В `members` входят активные членства с полями `id` (идентификатор членства), `username` и `can_manage_members`. Приглашения в сводке дополнены полем `recipient`, заявки — полем `applicant`. `join_code` содержит подписанный идентификатор организации, если она принимает заявки, и `null` в остальных случаях.

Приглашение содержит `id`, `organization_id`, `status` и `expires_at` в ISO 8601. Исходный токен доступен только в ответе на создание, который содержит заголовок `Cache-Control: no-store`. Для ручной передачи используйте ссылку вида `/organizations/invitations/#<token>`. Заявка содержит `id`, `organization_id` и `status`.

Сводка управления, выдача и отзыв приглашений и решение по заявке доступны владельцу и активным участникам с правом управления. Менять правила вступления и делегировать управление может только владелец с активным членством. Отвечать на приглашение может только его получатель.

Анонимный GET и анонимный изменяющий запрос с действительным CSRF-токеном возвращают HTTP 401. Ошибка CSRF или недостаточные права активного участника дают HTTP 403. Отсутствие активного членства на маршрутах управления, чужое приглашение и отсутствующая запись дают HTTP 404. Недействительная ссылка на заявку и выключенный режим заявок также дают HTTP 404. Конфликты состояния, включая повторное решение, возвращают HTTP 409. Ошибка схемы, отсутствие обоих идентификаторов приглашения или передача обоих возвращают HTTP 422.

## Подразделения

Маршруты относительны к `/api/v1/organizations/{org_id}/departments/`.

| Метод | Маршрут | Тело запроса | Успешный ответ |
|---|---|---|---|
| GET | Базовый маршрут | — | HTTP 200, плоский список подразделений, включая архивные, в порядке возрастания `id`. |
| POST | Базовый маршрут | `{"name":"Команда","description":"","parent_id":null}` | HTTP 201, новое подразделение. |
| GET | `{department_id}/` | — | HTTP 200, подразделение. |
| PATCH | `{department_id}/` | Изменяемые поля `name`, `description`, `parent_id`. | HTTP 200, обновлённое подразделение. |
| DELETE | `{department_id}/` | — | HTTP 204. Архивирует выбранный узел и всё поддерево. Повторный вызов также возвращает HTTP 204. |

Объект содержит `id`, `parent_id`, `name`, `description`, `is_archived`, `created_at` и `updated_at`. Поле `parent_id` связывает записи при построении дерева. Значение `null` обозначает корень. При создании обязательно только имя длиной от 1 до 200 символов после удаления пробелов по краям. По умолчанию описание пустое, а родитель отсутствует. Поле `is_archived` доступно для чтения.

Для чтения дерева нужны сессия Django и активное членство в организации. POST, PATCH и DELETE проверяют конкретное разрешение и его область. Для создания нужен доступ в области родителя, для перемещения — в исходной и целевой областях, для архивирования — на каждом действующем узле поддерева. Корень требует разрешения на уровне организации. Для изменения передайте CSRF-токен в заголовке `X-CSRFToken`.

Анонимные запросы с выполненной проверкой CSRF возвращают HTTP 401. Ошибка CSRF или отсутствие права управления у активного участника дают HTTP 403. Отсутствие активного членства, отсутствующее подразделение или родитель вне выбранной организации дают HTTP 404. Цикл, архивный родитель и попытка изменить архивное подразделение дают HTTP 409. Ошибка схемы возвращает HTTP 422.

Веб-страница `/organizations/{org_id}/departments/` строит дерево из этого API. Она доступна из карточки организации по ссылке «Открыть структуру».

### Членства и приглашения в подразделения

Маршруты относительны к `/api/v1/organizations`. В таблице `{department}` обозначает `/{org_id}/departments/{department_id}`. Для запросов требуется сессия Django. POST, PATCH и DELETE требуют заголовок `X-CSRFToken`.

| Метод | Маршрут | Параметры | Успешный ответ |
|---|---|---|---|
| GET | `{department}/members/` | `scope=branch`, `direct` или `others`. По умолчанию `branch`. | HTTP 200, каталог без дублей. |
| PATCH | `/{org_id}/department-directory-policy/` | `{"visibility":"branch"}` или `{"visibility":"organization"}`. | HTTP 204. |
| DELETE | `{department}/members/{membership_id}/` | Идентификатор прямого членства в подразделении. | HTTP 204, прямое членство завершено. |
| GET | `{department}/invitations/` | — | HTTP 200, история приглашений подразделения. |
| POST | `{department}/invitations/` | `{"organization_membership_id":123}`. | HTTP 201, новое приглашение. |
| DELETE | `{department}/invitations/{invitation_id}/` | — | HTTP 204, приглашение отозвано. |
| GET | `/department-invitations/` | — | HTTP 200, личный список приглашений в подразделения. |
| POST | `/department-invitations/{invitation_id}/respond/` | `{"decision":"accept"}` или `{"decision":"decline"}`. | HTTP 200, приглашение с итоговым статусом. |

Каталог возвращает `organization_membership_id`, `username` и массив `memberships` для каждого человека. Каждый элемент массива содержит `id` членства в подразделении, `department_id`, полный путь от корня в массиве `path` и признак прямого членства `is_direct`. `branch` включает прямых участников и участников потомков. `direct` выбирает только людей с прямым членством и сохраняет их остальные пути в той же ветке. `others` возвращает активных участников организации вне ветки с пустым массивом `memberships`, если это разрешает политика или право управления.

Приглашение содержит `id`, `organization_id`, `organization_name`, `department_id`, `department_name`, `organization_membership_id`, `username`, `status` и `created_at`. Личный список содержит приглашения текущего пользователя в организациях, где у него действует членство. Принятие приглашения создаёт или активирует прямое членство в подразделении.

По умолчанию действует видимость `branch`. Активный участник может открыть каталог ветки, если состоит в выбранном подразделении или одном из его потомков, либо имеет разрешение `departments.directory.read` в этой области. Политика `organization` или разрешение `departments.directory.read` на уровне организации открывают каталоги всех действующих подразделений и список людей вне ветки. Управление приглашениями требует `departments.invitations.manage` в подразделении, а завершение членства — `departments.members.manage` там же. Приглашать можно только участников, доступных в каталоге. Менять политику может только владелец. Отвечать на приглашение может только его получатель.

Чужие записи, недоступные ветки и архивные подразделения на маршрутах работы с членствами возвращают HTTP 404. Недостаточные права на изменение у активного участника дают HTTP 403. Повторное приглашение при наличии активного членства или ожидающего приглашения и повторный ответ на закрытое приглашение дают HTTP 409, если запись доступна. Ошибки схемы дают HTTP 422.

Веб-страницы каталога и личных приглашений доступны по `/organizations/{org_id}/departments/{department_id}/members/` и `/organizations/department-invitations/`.

## Роли и доступ

Маршруты относительны к `/api/v1/organizations/{org_id}`. Нужны сессия Django и активное членство. Для POST, PATCH и DELETE передайте `X-CSRFToken`. Веб-страница `/organizations/{org_id}/access/` показывает действующие разрешения и доступные операции с ролями.

| Метод | Маршрут | Запрос и успешный ответ |
|---|---|---|
| GET | `/permissions/` | HTTP 200, каталог `[{code,label,department_scoped}]`. |
| GET | `/permissions/effective/` | Необязательный query-параметр `department_id`. HTTP 200, `{permissions:[code]}` текущего участника. |
| GET | `/department-actions/` | HTTP 200, `root` с флагами `create`, `move` и `nodes` с флагами `create`, `update`, `move`, `archive`, `open_members` по идентификатору действующего узла. `open_members` отражает право открыть каталог участников подразделения. |
| GET | `/role-subjects/` | HTTP 200, активные членства организации с `id`, `username` и `department_memberships` (элементы `{id,department_id,name}`). |
| GET | `/roles/` | HTTP 200, роли организации, включая архивные. |
| POST | `/roles/` | `{"name":"Название","permissions":[{"code":"departments.update","include_descendants":false}]}`. HTTP 201, роль. |
| PATCH | `/roles/{role_id}/` | `name` и/или `permissions`. Переданный массив заменяет набор разрешений роли. HTTP 200, роль. |
| DELETE | `/roles/{role_id}/` | HTTP 204, роль архивирована, действующие назначения отозваны. |
| GET | `/role-assignments/` | HTTP 200, назначения ролей, включая отозванные. |
| POST | `/role-assignments/` | `{role_id,organization_membership_id,department_membership_id}`. HTTP 201, назначение. |
| DELETE | `/role-assignments/{assignment_id}/` | HTTP 204, назначение отозвано. |
| GET | `/positions/` | HTTP 200, назначения должностей, включая отозванные. |
| POST | `/positions/` | `{title,organization_membership_id,department_membership_id}`. HTTP 201, назначение должности. |
| DELETE | `/positions/{position_id}/` | HTTP 204, назначение должности отозвано. |

Роль содержит `id`, `name`, `is_archived` и `permissions`. Записи назначений дополнительно содержат `id` и `revoked_at`. Входное поле `department_membership_id` можно опустить или передать как `null` для области организации. Идентификатор подразделения и идентификатор членства в нём используются в разных полях.

Для чтения ролей, назначений, должностей и списка участников для назначения нужны `roles.read` или `roles.manage` на уровне организации. Для записи требуется `roles.manage`. Управляющий без статуса владельца может изменять и архивировать только роли без действующих назначений. Он может назначать или отзывать права других участников лишь в пределах собственных разрешений и их наследования. Передача `roles.manage` и изменение собственных назначений таким управляющим запрещены. `roles.read`, `roles.manage` и `organizations.onboarding.manage` действуют в области организации.

Отсутствие активного членства и чужие или отсутствующие записи дают HTTP 404. При отсутствии необходимого разрешения возвращается HTTP 403. Дубликаты действующих назначений, архивные роли и конфликты области дают HTTP 409. Ошибки схемы дают HTTP 422.

## Проекты

Веб-страницы `/organizations/{org_id}/projects/` и `/organizations/{org_id}/projects/{project_id}/` доступны из карточки организации. Для API нужны сессия Django и активное членство в организации. Для изменяющих запросов передайте `X-CSRFToken`.

Область проекта определяется действующим ответственным подразделением. Если его нет или оно архивировано, проверяются права на уровне организации. Участие подразделения и назначение руководителя сами по себе разрешений не выдают. Для чтения нужно `projects.view` в области проекта или активное прямое членство в проекте. Изменения требуют соответствующего разрешения из `projects.create`, `projects.update`, `projects.archive`, `projects.manage_departments` и `projects.manage_lead`. При смене ответственного подразделения доступ к просмотру проекта и управлению связями проверяется в исходной области, а в целевой области требуются `projects.view` и `projects.manage_departments`. При назначении участвующего подразделения проверяется право управления связями проекта и выбранного подразделения.

Статусы проекта — `draft`, `active`, `paused` и `completed`. Статус по умолчанию — `draft`. Даты начала и планового завершения необязательны. Если указаны обе даты, плановое завершение должно быть не раньше начала. Архивирование сохраняет карточку и связи. Архивные карточки остаются доступны для чтения в пределах обычных прав.

Маршруты относительны к `/api/v1/organizations/{org_id}`.

| Метод | Маршрут | Запрос и успешный ответ |
|---|---|---|
| GET | `/projects/` | HTTP 200, доступные проекты, включая архивные. |
| POST | `/projects/` | Обязательное `name`. Необязательные `description`, `status`, `start_date`, `planned_end_date`, `lead_membership_id` и `responsible_department_id`. HTTP 201, проект. |
| GET | `/projects/{project_id}/` | HTTP 200, проект. |
| PATCH | `/projects/{project_id}/` | Частичное изменение `name`, `description`, `status`, `start_date` и `planned_end_date`. HTTP 200, проект. |
| DELETE | `/projects/{project_id}/` | HTTP 204, проект архивирован. Повторный запрос с теми же правами возвращает HTTP 204. |
| PUT | `/projects/{project_id}/lead/` | `{"lead_membership_id":123}` или `null` в этом поле для снятия назначения. HTTP 200, проект. |
| PUT | `/projects/{project_id}/responsible-department/` | `{"responsible_department_id":123}` или `null` в этом поле для перевода в область организации. HTTP 200, проект. |
| PUT | `/projects/{project_id}/departments/{department_id}/` | HTTP 204, подразделение участвует в проекте. |
| DELETE | `/projects/{project_id}/departments/{department_id}/` | HTTP 204, связь с участвующим подразделением снята. |
| GET | `/project-options/` | Необязательный query-параметр `project_id`. HTTP 200, варианты для формы. |

Карточка содержит `id`, `name`, `description`, `status`, `start_date`, `planned_end_date`, `created_at`, `updated_at`, `is_archived`, `lead`, `responsible_department`, `participating_departments` и `permissions`. Даты передаются как `YYYY-MM-DD`. Допустимо `null` для очистки необязательной даты. Имя содержит от 1 до 200 символов после удаления пробелов по краям. Подразделение представлено полями `id`, `name` и `is_archived`. Руководитель представлен полями `id` (идентификатор членства) и `username`. В `permissions` входят флаги `update`, `archive`, `manage_departments` и `manage_lead` для этой карточки.

Варианты формы содержат `can_create_independent`, `can_manage_independent`, `can_set_independent`, `can_manage_independent_lead`, список действующих подразделений `departments` и список кандидатов `leaders`. Для каждого подразделения возвращаются `id`, `name`, `can_create`, `can_manage_departments`, `can_set_responsible` и `can_manage_lead`. Флаги `can_set_independent` и `can_set_responsible` учитывают права на просмотр и управление связями в целевой области при смене ответственного подразделения. Кандидаты включают только активных участников с активным аккаунтом. При создании они доступны, если пользователь вправе и создать проект, и назначить руководителя хотя бы в одной допустимой области. При указанном `project_id` сначала проверяется доступ к проекту, а выдача кандидатов требует права назначения руководителя в этом проекте.

Создание требует просмотра и права создания в выбранной области. Если указан ответственный отдел, дополнительно требуется право управления подразделениями проекта. Если указан руководитель, дополнительно требуется право его назначения. Чужой, отсутствующий или скрытый проект, а также связанная запись из другой организации возвращают HTTP 404. Недостаток разрешений даёт HTTP 403. Изменение архивного проекта, назначение архивного подразделения или неактивного руководителя дают HTTP 409. Ошибки схемы и некорректный порядок дат дают HTTP 422.

### Команды и запросы специалистов

Веб-страницы доступны по `/organizations/{org_id}/projects/{project_id}/team/`, `/organizations/{org_id}/staffing/`, `/organizations/{org_id}/staffing/{request_id}/` и `/organizations/project-invitations/`.

Маршруты в таблице относительны к `/api/v1/organizations`. `{project}` обозначает `/{org_id}/projects/{project_id}`, а `{request}` — `/{org_id}/staffing-requests/{request_id}`. Требуется сессия Django, для изменяющих запросов также `X-CSRFToken`.

|---|---|---|

| GET | `{project}/staffing-requests/` | HTTP 200, запросы проекта, включая черновики. |

Ответ команды содержит `lead`, `members`, `can_view_team`, `can_manage_team` и `can_request`. Запись состава содержит `id`, `username`, `source_department_name`, `is_active`, `joined_at` и `ended_at`. Состав доступен активному члену проекта или при `projects.team.view` и доступе к карточке. Руководитель, который вправе запрашивать специалистов, может получить форму запроса с пустым массивом `members`, если у него нет доступа к составу. Завершение членства требует `projects.team.manage` и доступа к карточке.

Запрос содержит идентификаторы и названия проекта и подразделения, поля запроса, статус, `created_at`, `updated_at`, `submitted_at`, `handled_by`, `handled_at`, `comment`, счётчики `accepted_count` и `pending_count`, флаги `can_edit`, `can_cancel`, `can_allocate`, `awaiting_handler` и массив `history`. Элемент истории содержит `id`, `username`, `department_name`, `status`, `mode`, `created_at`, `resolved_at`, `allocated_by` и `can_revoke`. Списки запросов возвращают пустой массив истории. Приглашение в личном списке содержит `id`, `organization_name`, `project_name`, `department_name`, `status` и `created_at`.

Запрос проходит состояния `draft`, `sent`, `partial`, `fulfilled`, `rejected` и `cancelled`. В черновике или открытом запросе можно изменить сведения. Количество специалистов и указанная длительность должны быть положительными целыми числами. Максимальная длина специализации — 200 символов. После отправки количество мест нельзя уменьшить ниже суммы принятых и ожидающих назначений. Распределение и отказ доступны для `sent` и `partial`. При `direct` запись сразу получает статус `accepted`. При `invitation` статус `pending` резервирует место. Принятие, отказ и отзыв завершают ожидающую запись. При подсчёте выполнения учитываются только принятые назначения.

Руководитель может создавать, отправлять, менять и отменять запрос своего проекта при `projects.staffing.request` в его области и доступе к карточке. Эти операции также доступны владельцу с активным членством. На стороне подразделения `departments.staffing.allocate` ограничивает доступ целевым подразделением и областями прямых членств кандидатов. Руководителю проекта доступна история его запроса, а распределяющему — записи в его области. Политику назначения меняет владелец. Ответить на приглашение может его получатель.

Чужие и скрытые записи дают HTTP 404. Отсутствие права на видимый объект или ошибка CSRF дают HTTP 403. Повторный ответ, превышение числа мест или конфликт состояния дают HTTP 409. Ошибки схемы дают HTTP 422.

## Задачи

Веб-страницы доступны по `/organizations/{org_id}/tasks/`, `/organizations/{org_id}/tasks/mine/`, `/organizations/{org_id}/tasks/{task_id}/` и `/organizations/{org_id}/projects/{project_id}/tasks/`. Владелец меняет режим назначения через существующую страницу `/organizations/{org_id}/settings/`. Форма отправляет POST с CSRF-токеном, `action=task_assignment_mode` и `task_mode=department` или `task_mode=direct`.

Для запросов API нужны сессия Django и активное членство в организации. Для изменяющих запросов передайте `X-CSRFToken`. В обычном списке чтение требует `tasks.view` в области задачи или участия в задаче в качестве автора, основного исполнителя либо активного соисполнителя. Для задачи проекта дополнительно проверяется доступ к проекту. Уполномоченный участник очереди может открыть карточку в пределах текущего поручения или этапа проверки. Права на проект и на изменение задачи определяются отдельно.

Область задачи задаёт её действующее подразделение. В остальных случаях используются область проекта или разрешения на уровне организации. Для создания нужны `tasks.view` и `tasks.create` в целевой области, для редактирования — `tasks.update`, для изменения статуса — `tasks.change_status`, для архивирования — `tasks.archive`. Перенос между подразделениями требует права обновления в обеих областях и сохранения доступа на чтение.

Назначение основного исполнителя и соисполнителей требует `tasks.assign` и режима `direct`. У проектной задачи его выполняет руководитель проекта, а кандидат должен активно состоять в проекте. Для назначения в самостоятельной задаче кандидат должен иметь активное членство в организации. Основной исполнитель и соисполнители задаются отдельными операциями. При `department` прямое назначение недоступно.

Новая задача имеет статус `pending`. Операция изменения статуса позволяет начать работу при действующем основном исполнителе и отменить открытую задачу. Переход в `review` выполняется отправкой результата, возврат в `in_progress` — решением о доработке, а переход в `completed` — принятием последнего обязательного этапа. При завершении сервер заполняет `completed_at`. Даты начала и срока необязательны. Передавайте их в ISO 8601 со смещением или `Z`. Срок не может быть раньше планового начала.

Маршруты относительны к `/api/v1/organizations/{org_id}`. `{task}` обозначает `/tasks/{task_id}`.

| Метод | Маршрут | Запрос и успешный ответ |
|---|---|---|
| GET | `/tasks/` | HTTP 200, страница списка. |
| POST | `/tasks/` | Обязательное `name`. Необязательные `description`, `priority_id` или `priority`, `project_id`, `department_id`, `parent_id`, `planned_start_at`, `due_at`, `assignee_id`. HTTP 201, задача. |
| GET | `{task}/` | HTTP 200, задача. |
| PATCH | `{task}/` | Изменяемые поля `name`, `description`, `priority_id` или `priority`, `department_id`, `planned_start_at`, `due_at`. HTTP 200, задача. |
| DELETE | `{task}/` | HTTP 204, задача архивирована. |
| PUT | `{task}/assignee/` | `{"assignee_id":123}` или `{"assignee_id":null}`. Идентификатор относится к членству в организации. HTTP 200, задача. |
| PUT | `{task}/collaborators/{membership_id}/` | HTTP 204, участник добавлен в соисполнители. |
| DELETE | `{task}/collaborators/{membership_id}/` | HTTP 204, соисполнение прекращено. |
| PUT | `{task}/status/` | Например, `{"status":"in_progress"}`. HTTP 200, задача. |
| GET | `/task-options/` | Необязательный query-параметр `task_id`. HTTP 200, варианты для формы. |
| GET | `/task-assignee-options/` | Необязательные query-параметры `project_id`, `department_id`, `parent_id`. HTTP 200, варианты назначения при создании. |

Ответ списка содержит `items`, `total`, `page` и `page_size`. Задачи отсортированы по убыванию идентификатора. Параметры запроса: `q` (поиск по названию и описанию), `status`, `project_id`, `department_id`, `mine`, `include_archived`, `distribution_pending`, `queue`, `page` (с 1), `page_size` (от 1 до 100, по умолчанию 20). По умолчанию архивные задачи скрыты. Для списка проекта или подразделения укажите соответствующий идентификатор. `mine=true` возвращает задачи, в которых пользователь основной исполнитель или активный соисполнитель. `distribution_pending=true` оставляет задачи с ожидающим распределением. Для очереди распределения задайте `queue=distribution`, для очереди проверки — `queue=review`.

Ответ задачи содержит `id`, `name`, `description`, `status`, `priority`, `planned_start_at`, `due_at`, `completed_at`, `created_at`, `updated_at`, `is_archived`, `distribution_pending`, `author`, `assignee`, `collaborators`, `project`, `department`, `permissions` и `allowed_statuses`. Люди представлены идентификатором членства и `username`, проект и подразделение — полями `id` и `name`. В `permissions` возвращаются флаги `update`, `assign`, `archive` и `change_status`. Для имени допустимы 1–200 символов после удаления пробелов по краям. Необязательные даты и подразделение можно очистить через `null`.

Варианты формы содержат `assignment_mode`, `current_membership_id`, `can_create_standalone`, `can_clear_department`, `departments`, `projects` и `assignees`. Подразделения содержат `id`, `name`, `can_create`, `can_update`. Проекты содержат `id`, `name`, `can_create` и `department_ids`, где возможно создание задачи. Кандидаты `assignees` выдаются только для видимой задачи при действующем праве назначения.

`GET /task-assignee-options/` возвращает `{assignment_mode,can_assign,candidates}` для будущей задачи с заголовком `Cache-Control: no-store`. Каждый кандидат содержит `id` членства в организации и `username`. При указанном `parent_id` пропущенные `project_id` и `department_id` наследуются от родителя. Архивное подразделение родителя пропускается. Значение `0` в одном из этих query-параметров явно выбирает отсутствие проекта или подразделения. Для указанного родителя нужны доступ на чтение и право изменения. При допустимой области без права прямого назначения возвращаются `can_assign=false` и пустой список. Отсутствие права изменения видимого родителя даёт HTTP 403, чужой или скрытый объект — HTTP 404, архивная область — HTTP 409.

`assignee_id` в `POST /tasks/` и `POST {task}/subtasks/` задаёт основного исполнителя в той же транзакции, что и создание. Пропущенное поле или `null` создаёт задачу без исполнителя. Сервер проверяет режим организации, полномочия и действующее членство кандидата по тем же правилам, что при назначении в существующей задаче. При ошибке назначения новая задача и запись истории не сохраняются.

Чужая, отсутствующая или скрытая запись даёт HTTP 404. Недостаток прав на видимую задачу и ошибка CSRF дают HTTP 403. Конфликт состояния, включая попытку изменить архивную задачу, назначение в режиме `department`, недопустимый переход или повторное добавление соисполнителя, даёт HTTP 409. Ошибки схемы и порядок дат дают HTTP 422.

### Распределение и проверка

Очереди доступны на веб-страницах `/organizations/{org_id}/tasks/distribution/` и `/organizations/{org_id}/tasks/reviews/`. Операции распределения и проверки используют ту же сессию Django и CSRF-защиту. В таблице используются прежние сокращения пути и тот же префикс организации.

| Метод | Маршрут | Запрос и успешный ответ |
|---|---|---|
| GET | `{task}/workflow/` | HTTP 200, распределение, маршрут, текущий этап и доступная история. |
| POST | `{task}/distribution/` | HTTP 204, задача направлена на распределение. |
| PUT | `{task}/distribution/` | `{"assignee_id":123}`. HTTP 204, назначен основной исполнитель. |
| POST | `{task}/review/submissions/` | `{"comment":"Результат","links":["https://example.com/result"]}`. HTTP 204, сохранена новая версия результата. |
| POST | `{task}/review/decisions/` | `{"stage_id":123,"outcome":"approved"}` или `outcome=returned` с непустым `comment`. HTTP 204, сохранено решение. |
| PUT | `{task}/review/policy/` | `policy` или `null` для наследования, необязательный `reviewer_id` для задачи без проекта. HTTP 204. |
| GET | `/task-review-policy/` | HTTP 200, `{policy,can_manage}` организации. |
| PUT | `/task-review-policy/` | `{"policy":"department"}`. HTTP 204. |
| GET | `/projects/{project_id}/task-review-policy/` | HTTP 200, `{policy,can_manage}` проекта. |
| PUT | `/projects/{project_id}/task-review-policy/` | `policy` или `null` для наследования. HTTP 204. |

В `workflow.distribution` возвращаются `pending`, `can_route`, `can_allocate`, `candidates` и `history`. Запись истории содержит статус, режим, подразделение, исполнителя, инициатора и автора решения, а также время создания и обработки. Кандидаты доступны уполномоченному распределяющему для текущего поручения.

В `workflow.review` возвращаются `policy`, `override`, `reviewer_id`, `can_manage`, `reviewers`, `can_submit`, `can_approve`, `can_return`, `current_stage_id`, `current_stage_kind` и `submissions`. Версия содержит `id`, `comment`, `links`, `created_at`, `submitted_by` и `stages`. Этап содержит `id`, `kind`, `position` и `decision`. Решение содержит `outcome`, `comment`, `actor` и `created_at`. Для комментария допустимо до 5000 символов, для версии результата — до 10 ссылок HTTP(S).

Для направления требуется `tasks.route` в действующем ответственном подразделении, ожидающая задача без исполнителя и режим `department`. Очередь видна по `tasks.distribution.view` или `tasks.distribute` в области подразделения. Выбор исполнителя требует `tasks.distribute`. Доступ к кандидатам учитывает активное членство в ответственном подразделении или доступных потомках и активное членство в проекте для проектной задачи.

Политики проверки — `project`, `department` и `department_project`. У задачи приоритет перед проектом, у проекта перед организацией. Управление требует `tasks.review.manage` в соответствующей области. Результат отправляет действующий основной исполнитель с `tasks.review.submit`. Решение требует `tasks.review.approve` или `tasks.review.return` на текущем этапе. Этап проекта доступен действующему руководителю этого проекта, а явный этап — назначенному проверяющему. Решение самого исполнителя или отправителя запрещено.

После возврата следующая отправка создаёт новую версию и начинает проверку с первого этапа. Решение передаёт `stage_id`, чтобы устаревшая вкладка не могла принять другой этап. Конфликт состояния или устаревший этап дают HTTP 409, отсутствие прав — HTTP 403 или 404 в зависимости от доступа к записи, а ошибки запроса, включая возврат без пояснения, — HTTP 422.

Страница дерева содержит `items`, `total`, `completed`, `page` и `page_size`. Подзадача представлена полями `id`, `parent_id`, `name`, `status`, `workflow_status`, `assignee`, `due_at`, `is_archived`, `permissions` с флагами `update` и `archive`, а также `can_move`. Порядок — по возрастанию идентификатора, размер страницы от 1 до 100, по умолчанию 50. Счётчики относятся к доступным потомкам.

Обычная задача теперь содержит `parent_id`, `parent`, `can_view_decomposition` и `has_unfinished_children`. Последний флаг отмечает наличие незавершённых прямых подзадач вне архива и служит для предупреждения при закрытии родителя. Создание через `POST /tasks/` также допускает `parent_id`. Если при создании подзадачи проект или подразделение не переданы, они наследуются от родителя. Явное `null` отменяет наследование этого поля. Просмотр родителя и подзадач проверяется отдельно. Идентификатор и название скрытого родителя не выдаются.

Чек-лист содержит `id`, `name`, `completed`, `total` и `items`. Пункт содержит `id`, `name`, `position`, `is_completed`, `completed_at` и `completed_by`. При снятии отметки время и автор выполнения очищаются. Сводка декомпозиции возвращает `can_manage`, `can_create_subtask`, `can_move`, `can_convert_to_item`, `convert_to_item_reason`, `checklists` и `conversions`. Записи преобразований содержат направление, исходный или созданный пункт, автора и время. Ссылка на подзадачу возвращается только при доступе к ней.

Чтение подзадач и чек-листов следует обычным правилам просмотра задач. Для изменения чек-листов требуется `tasks.update` на задаче. Создание подзадачи требует права изменить родителя и обычных прав создания в области подзадачи. Перенос проверяет право изменения задачи и прежнего и нового родителей. Обратное преобразование требует также `tasks.archive` на подзадаче и подтверждения. Преобразуется подзадача в ожидании с той же областью, что у родителя, без собственных сроков, описания, нестандартного приоритета, маршрута проверки, исполнителей, дочерних записей или значимой истории. Цикл, недопустимая конверсия и неполный порядок дают HTTP 409, отсутствие подтверждения даёт HTTP 422.

### Зависимости

Маршруты относительны к `/api/v1/organizations/{org_id}`. `{task}` обозначает `/tasks/{task_id}`. Для записи нужны CSRF-токен и `tasks.update` в области зависимой задачи. Для создания связи также требуется доступ к предшествующей задаче.

| Метод | Маршрут | Запрос и успешный ответ |
|---|---|---|
| GET | `{task}/dependencies/` | HTTP 200, `{can_manage,blocked,items}`. |
| POST | `{task}/dependencies/` | `{"predecessor_id":123,"kind":"strict"}` или `kind=informational`. HTTP 201, созданная связь. |
| DELETE | `{task}/dependencies/{dependency_id}/` | HTTP 204, связь удалена. |

Элемент `items` содержит `id` связи, `kind`, `unresolved` и `predecessor`. Для доступного предшественника возвращаются `id`, `name` и `status`. Для скрытого предшественника возвращается `predecessor: null`, а признак незавершённости остаётся доступен. `blocked` означает, что задача находится в ожидании и у неё есть незавершённый строгий предшественник.

Ответ задачи содержит флаги `has_blocking_dependencies` и `has_dependency_warnings`. Строгая связь блокирует как `PUT {task}/status/` с переходом из `pending` в `in_progress`, так и `POST {task}/review/submissions/` из `pending`. Завершённой считается предшествующая задача со статусом `completed`. Информационные связи показывают предупреждение, сохраняя доступ к началу работы. Добавление связи к уже выполняющейся задаче не меняет её статус.

Чужая или недоступная запись даёт HTTP 404. Самоссылка, повторная связь, цикл, попытка начать заблокированную задачу и обратное преобразование задачи с любой зависимостью дают HTTP 409.

### Приоритеты

Справочник доступен в веб-разделе «Рабочие процессы» по `/organizations/{org_id}/tasks/configuration/`. Маршруты API относительны к `/api/v1/organizations/{org_id}`. Для чтения справочника требуется доступ к конфигурации рабочих процессов. Для изменений нужны `tasks.priorities.manage` на уровне организации и заголовок `X-CSRFToken`.

| Метод | Маршрут | Запрос и успешный ответ |
|---|---|---|
| GET | `/task-priorities/` | HTTP 200, `{can_manage,items}`. |
| POST | `/task-priorities/` | `code`, `name`, `rank`, `color`, необязательные `sort_order` и `is_default`. HTTP 201, уровень. |
| PATCH | `/task-priorities/{priority_id}/` | Изменяемые поля `name`, `rank`, `color`, `sort_order`, `is_default`. HTTP 200, уровень. |
| DELETE | `/task-priorities/{priority_id}/` | HTTP 204, уровень архивирован. |

Уровень содержит `id`, `code`, `name`, `rank`, `color`, `sort_order`, `is_active` и `is_default`. Код уникален в организации и после создания неизменяем. Ранг — целое число, порядок — неотрицательное целое число. Цвет задаётся как `#RRGGBB`. Справочник включает архивные уровни и сортируется по `sort_order`, затем по идентификатору. `is_default=true` назначает новый уровень по умолчанию и снимает отметку с прежнего в той же транзакции. Архивирование текущего уровня по умолчанию, используемого уровня или одного из стандартных уровней даёт HTTP 409.

При создании или редактировании задачи передавайте `priority_id` для выбора активного уровня организации. Прежнее поле `priority` принимает `low`, `normal` или `high`. Одновременная передача обоих полей даёт HTTP 422. При создании без этих полей применяется активный уровень по умолчанию, при обновлении уровень сохраняется. Выбор чужого уровня даёт HTTP 404, архивного — HTTP 409.

Ответ задачи содержит `priority_level` с полями `id`, `code`, `name`, `rank`, `color`. Поле `priority` сохраняет стандартный код для совместимости. Для пользовательских уровней его значение — `normal`. `GET /task-options/` содержит список активных уровней в `priorities`. В `GET /tasks/` фильтр `priority_id` выбирает уровень, а `sort=priority` сортирует по убыванию ранга, затем по убыванию идентификатора задачи.

### Пользовательские статусы и переходы

Маршруты относительны к `/api/v1/organizations/{org_id}`. `{task}` обозначает `/tasks/{task_id}`. Для чтения справочников нужны активное членство и `tasks.workflow.view` либо любое из разрешений управления конфигурацией. Статусы изменяются с `tasks.statuses.manage`, правила переходов — с `tasks.transitions.manage`. Эти разрешения относятся к уровню организации. Изменяющие запросы требуют заголовок `X-CSRFToken`.

| Метод | Маршрут | Запрос и успешный ответ |
|---|---|---|
| GET | `/task-statuses/` | HTTP 200, `{can_manage,items}`. |
| POST | `/task-statuses/` | `code`, `name`, `stage`, `color`, необязательные `sort_order` и `is_default`. HTTP 201, статус. |
| PATCH | `/task-statuses/{status_id}/` | `name`, `color`, `sort_order` и/или `is_default`. HTTP 200, статус. |
| DELETE | `/task-statuses/{status_id}/` | HTTP 204, статус архивирован. |
| GET | `/task-transitions/` | HTTP 200, `{can_manage,items,permission_options,stage_targets}`. |
| POST | `/task-transitions/` | `from_status_id`, `to_status_id`, необязательные `is_enabled`, `allow_assignee` и `required_permissions`. HTTP 201, правило. |
| PATCH | `/task-transitions/{transition_id}/` | `is_enabled`, `allow_assignee` и/или `required_permissions`. HTTP 200, правило. |
| GET | `{task}/workflow-status/` | HTTP 200, `{current,allowed_workflow_statuses}`. |
| PUT | `{task}/workflow-status/` | `{"status_id":123,"expected_status_id":456}`. HTTP 200, задача. |

Статус в справочнике содержит `id`, `code`, `name`, `stage`, `color`, `sort_order`, `is_active` и `is_default`. Код, этап и организация после создания неизменяемы. `is_default=true` заменяет активный статус по умолчанию для этого этапа в одной транзакции. Для архивации текущего статуса по умолчанию сначала выберите другой. Архивный статус сохраняется в прежних задачах и может быть исходным для перехода, пока доступно действующее правило. Для новых назначений доступны активные статусы.

Правило содержит `id`, `from_status_id`, `to_status_id`, `is_enabled`, `allow_assignee` и `required_permissions`. По умолчанию правило включено, исполнитель не допущен и список дополнительных разрешений пуст. `permission_options` содержит допустимые пары `{code,label}`, а `stage_targets` перечисляет допустимые целевые этапы для каждого исходного этапа. Для отключения правила задайте `is_enabled=false`.

Карточка задачи сохраняет системное поле `status` и возвращает `workflow_status` и `allowed_workflow_statuses`. Пользовательский статус в этих полях и в строке подзадачи содержит `id`, `code`, `name`, `stage` и `color`. `GET /task-options/` возвращает активные статусы в `statuses`. `GET /tasks/` принимает `workflow_status_id` для фильтрации, `status` для фильтра по этапу и `sort=status` для сортировки по возрастанию порядка статуса, затем по убыванию идентификатора задачи.

Для ручного перехода требуется `tasks.change_status` в области задачи либо, если правило допускает исполнителя, назначение основным исполнителем и `tasks.status.execute` в той же области. Дополнительно проверяются все разрешения правила. `expected_status_id` должен совпасть с текущим статусом, иначе сервер отвечает HTTP 409. Старый `PUT {task}/status/` сохраняет пользовательский статус, если передан текущий этап. Для другого этапа он выбирает действующий статус по умолчанию и проверяет тот же набор правил. Ручные переходы допускаются внутри этапа, при начале работы и при отмене открытой задачи. Операции согласования при смене этапа применяют его статус по умолчанию независимо от настроек ручных переходов. Проверка строгих зависимостей сохраняется при начале работы.

## Календарь

Веб-страница `/organizations/{org_id}/calendar/` доступна из боковой панели организации. API использует сессию Django и активное членство в организации маршрута. Изменяющие запросы требуют `X-CSRFToken`.

Маршруты относительны к `/api/v1/organizations/{org_id}`.

| Метод | Маршрут | Запрос и успешный ответ |
|---|---|---|
| GET | `/calendar/` | Параметры диапазона и фильтры. HTTP 200, `{items}` со встречами, мероприятиями и дедлайнами. |
| GET | `/calendar/filters/` | HTTP 200, варианты проектов и подразделений и флаги создания. |
| GET | `/events/` | Параметры диапазона и фильтры. HTTP 200, `{items}` со встречами и мероприятиями. |
| POST | `/events/` | Поля события. HTTP 201, событие. |
| GET | `/events/{event_id}/` | HTTP 200, событие. |
| PATCH | `/events/{event_id}/` | Изменяемые поля запланированного события. HTTP 200, событие. |
| POST | `/events/{event_id}/cancel/` | HTTP 200, отменённое событие. |
| POST | `/events/{event_id}/archive/` | HTTP 200, архивное событие. |

Для чтения событий требуется `calendar.read` в их области. Для проектного события также проверяется доступ к проекту. Если заполнены и проект, и подразделение, разрешение проверяется для обеих областей. Для создания нужен `calendar.create`, для изменения — `calendar.update`, для отмены — `calendar.cancel`, для архива — `calendar.archive`. При создании связанного события и смене области дополнительно требуется `calendar.manage_scope`. Смена области проверяет полномочия в исходной и целевой областях. Авторство само по себе прав не выдаёт.

Запросы диапазона принимают даты `start` и `end` в формате `YYYY-MM-DD` и необязательную IANA-зону в параметре `timezone` (по умолчанию `UTC`). `start` включается, `end` исключается, длина диапазона — от 1 до 42 календарных дней. В выборку входят события, пересекающие диапазон, и дедлайны в его пределах. Фильтры `project_id` и `department_id` используют прямые связи записи. `source` принимает `meeting` или `event`, а для объединённой ленты также `task_deadline`. `include_archived=true` включает архивные записи. Отменённые события видны со статусом `cancelled`.

При создании обязательны `title`, `type` (`meeting` или `event`), `starts_at`, `ends_at` и `timezone`. Необязательны `description`, `all_day`, `location`, `online_url`, `project_id` и `department_id`. Заголовок содержит до 200 символов после удаления пробелов по краям, место — до 240. Онлайн-ссылка должна использовать HTTP(S). При обновлении `null` очищает место, ссылку, проект или подразделение.

Для обычного события передавайте `starts_at` и `ends_at` в ISO 8601 с часовым смещением. Окончание должно быть позже начала. Для `all_day=true` обе границы задаются первым допустимым моментом соответствующей даты в зоне события, конец исключается. Обычно это полночь. При переходе часов, пропускающем полночь, используется первый момент после перехода. Для события на один день укажите начало этого дня и начало следующего. При просмотре такого события в другом поясе сохраняются даты зоны события.

Дедлайн имеет `source=task_deadline`, идентификатор исходной задачи, ссылку на её карточку и текущий пользовательский статус в `status_label`. Дедлайны задач и подзадач выбираются с проверкой обычной видимости задачи. Изменение `due_at` отражается в следующей календарной выборке.

Общие поля записи включают `id`, `source`, `title`, `description`, `starts_at`, `ends_at`, `timezone`, `all_day`, `status`, `status_label`, `project_id`, `department_id`, `location`, `online_url`, `url`, `can_edit`, `can_cancel` и `can_archive`. Для дедлайна `ends_at` имеет значение `null`. Идентификаторы разных источников могут совпадать. Используйте пару `(source, id)`. Маршруты событий дополнительно возвращают `type`, `can_manage_scope`, `created_at` и `updated_at`. `/calendar/filters/` возвращает `projects` и `departments` с элементами `{id,name,can_create}`, а также `can_create` и `can_create_organization`.

Недоступная организация, скрытое событие или чужой связанный объект дают HTTP 404. Недостаток права на действие или ошибка CSRF дают HTTP 403. Попытка изменить отменённое или архивное событие либо привязать архивный проект или подразделение даёт HTTP 409. Некорректный диапазон, интервал или часовой пояс дают HTTP 422.
