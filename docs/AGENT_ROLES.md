# Регламент субагентов Codex — Enactus OS

**Общий принцип:** один главный Codex Coordinator/Tech Lead разбивает требования `docs/TECHNICAL_SPEC.md` на инкременты, оформляет интерфейсные контракты и делегирует НЕЗАВИСИМЫЕ задачи. Каждый субагент имеет узкую ответственность. Параллельность не должна ценой конфликтов ухудшать проект.

| Имя custom agent | Когда подключать | Основной scope | Не делать |
|---|---|---|---|
| `backend` | Django/REST/бизнес-операции | `apps/`, backend-сервисы, schemas, endpoints, permission guards; **миграции только по эксклюзивному назначению** | React, CSS, чужие миграции, инфраструктурные файлы без задания |
| `frontend` | Веб-страницы и UX | `templates/`, `static/`, страницы и Vanilla JS; API-контракт читается, но не меняется | `models.py`, миграции, `config/settings.py` |
| `database` | Дизайн схемы, индексов, query review, безопасность связей | `docs/ERD.md` и review; **по умолчанию только аналитика, без модели и миграций** | Параллельное редактирование ORM-моделей backend-агента |
| `qa_security` | При каждом функциональном инкременте и обязательно на auth/RBAC | `tests/` и отчёты; тесты доступа, границ tenant, CSRF/IDOR; review | Исправлять рабочие файлы параллельно backend/frontend |
| `devops` | Docker/локальный запуск/CI | `Dockerfile`, `compose.yaml`, `.env.example`, `.gitignore`, скрипты и CI | БД старого проекта, чужие volumes, логика домена |
| `calendar` | Фаза календаря MVP | отдельный `apps/calendar/`, контракты RSVP/recurrence | Сетевые интеграции с Google Calendar в MVP и общие маршруты без согласования |
| `docs_reviewer` | По запросу координатора после этапов | документация, consistency check и CHANGELOG | Переписывать согласованные бизнес-требования без решения владельца |

## Практические правила выполнения

1. **До старта делегации:** главный агент фиксирует задачу, входные артефакты, выходные файлы, ownership, API/DB-контракты, тесты. Если контракт неизвестен — сначала короткое проектирование, затем код.
2. **Параллельно допустимо:** frontend готовит статическую страницу по утверждённому API-контракту; backend реализует этот контракт; QA пишет независимые тесты в `tests/`; DB reviewer проверяет схему только для чтения.
3. **Параллельно недопустимо:** две ветки правят `config/urls.py`; два агента добавляют разные `0002_*.py` в одном Django-приложении; frontend самостоятельно меняет формы backend без контракта; DevOps удаляет Postgres volume при тестировании.
4. **Общие файлы:** `config/settings.py`, `config/urls.py`, `pyproject.toml`, `compose.yaml`, migration files, permissions policy registry — интегрирует только главный агент или один агент по явному эксклюзивному назначению.
5. **Блокировки:** субагент не расширяет scope при препятствии, а сообщает причину главному агенту.
6. **Ревью:** `qa_security` обязан независимо проверить любое изменение RBAC, auth/session/CSRF, приглашений, смены владельца, cross-org FK и выдачи данных в интерфейс.
7. **Отчёт каждого агента:** что изучил, что сделал, какие файлы трогал, фактические тесты (или почему не выполнены), предупреждения, передача результата координатору.
8. **Главный агент:** проверяет `git diff`, совместимость контрактов, миграций и UI, запускает smoke/integration tests и только после этого сообщает готовность этапа.

## Шаблон поручения субагенту

```text
Задача / ID:
Цель и acceptance criteria:
Входные контракты (с точными именами/версиями):
Разрешённые файлы и каталоги:
Запрещённые файлы/операции:
Тесты и команды проверки:
Отчёт для координатора: изменения, evidence, риски, блокеры.
```

## Первая фаза: кому что делегировать

- **Coordinator:** выбирает новый путь проекта, инициализирует Git, фиксирует структуру и контракты; не допускать доступа к старому `enactusos`.
- **DevOps:** предлагает/создаёт Docker/Compose и `.env.example`, не запуская разрушительных команд; проверяет свободные порты.
- **Backend:** создаёт Django-каркас, заранее выбирает кастомную модель `User`, подключает Ninja и healthcheck без бизнес-модулей; скоординировать создание миграций с координатором.
- **Database:** проверяет модель User и безопасную инициализацию PostgreSQL **без правок** backend-файлов.
- **QA/Security:** пишет самый первый smoke-check/тест и проверяет невыдачу секретов.
- **Frontend:** не нужен до согласования маршрутов/UI контрактов; не запускать «на всякий случай».

**Примечание:** текстовая инструкция «read-only» не создаёт sandbox. Убедитесь, что делегированный агент реально соблюдает границы; используйте отдельные ветки/worktrees, когда это оправдано.
