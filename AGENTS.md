# AGENTS.md — Enactus OS / Codex

## Прежде всего
- Это **НОВЫЙ** проект Enactus OS с нуля. Главный источник требований: `docs/TECHNICAL_SPEC.md` (полное ТЗ, редакция 3.0).
- Прежний `/home/stanislav/it/enactusos` и его PostgreSQL, Docker volumes, миграции, исходники и `.env` **не использовать, не изменять, не копировать, не удалять**. Другие проекты пользователя тоже не трогать.
- В этом каталоге пока **только ТЗ, инструкции и определения субагентов**, а не приложение. Код, БД и Git создать заново в этом каталоге.
- Предполагаемый стек: Python + Django + Django Ninja + PostgreSQL 16, Docker Compose, Django Templates + **Vanilla HTML/CSS/JavaScript (ES Modules)**. **Не использовать React/Vue/Next.js.**

## MVP и продуктовые инварианты
- Первая пилотная организация Enactus Toraighyrov, но архитектура универсальная и multi-tenant. Запрещены межорганизационные утечки через API/ORM/фоновые задачи.
- В MVP обязательно: пользователи, организации, владельцы/админы; вложенные подразделения/несколько членств; ограниченные роли и наследование; проекты; запросы специалистов руководителю профильного отдела; задачи и маршруты проверки; уведомления/аудит; панель; **полноценный внутренний календарь (день/неделя/месяц, дедлайны задач, встречи/мероприятия, приглашения, три режима RSVP, повторения)**.
- Не кодировать названия Project/HR/PR/Event в бизнес-логике: это первоначальные данные одной организации, задаваемые через UI. Не создавать автоматически финансы и Speakers.
- После MVP (не включать в текущий scope): утверждение протоколов, файловая библиотека с версиями, конструктор отчётов и аналитики, внешние интеграции и токены, создание организаций из шаблонов/копированием. Проектировать расширяемость без написания ненужного кода.
- Подробные определения, проверки, сценарии AT-01…AT-18 и маршруты API — в `docs/TECHNICAL_SPEC.md`.

## Как действовать
1. Перед изменениями прочитать `docs/TECHNICAL_SPEC.md`, `docs/AGENT_ROLES.md` и текущий `git status` (если Git уже инициализирован). Сначала выяснить, существует ли уже новый каркас. Не переинициализировать работающую систему без согласования.
2. Планировать **один небольшой завершённый инкремент**. В начале назвать цель, затрагиваемые файлы, ответственные роли/субагенты и критерии приёмки. Не делать всё MVP одним огромным коммитом.
3. **Использовать настоящих Codex-субагентов для независимых задач**, когда они доступны. Координатор распределяет направления: `backend`, `frontend`, `database`, `qa_security`, `devops`, `calendar` (когда наступит её фаза), `docs_reviewer`. Для маленькой последовательной задачи не требуется формальное делегирование. Никогда не заявлять об использовании субагентов, если они не были реально запущены.
4. **Никаких одновременных правок одного файла или конкурирующих миграций.** Контракт API/DB сначала согласует координатор. Разрешение конфликтов, регистрация Django-приложений, общие settings/urls и интеграционное тестирование — за главным агентом. Субагенты получают ограниченный scope (см. `docs/AGENT_ROLES.md`).
5. Кодекс **сам создаёт и изменяет файлы в новом репозитории**; пользователь не должен переписывать десятки файлов вручную. В конце показывать diff, список затронутых файлов, фактические команды, тесты и результат; не выдавать «готово» без запуска проверок.
6. Создавать тесты со свежего репозитория, включая положительные, отрицательные и cross-tenant случаи. Менять модель пользователя надо **до первых миграций**. Секреты — в `.env`, но сам `.env` не коммитить; положить `.env.example` с безвредными плейсхолдерами.
7. Не запускать `docker compose down -v`, не удалять volumes/БД, не чистить чужие контейнеры и не делать опасные команды по умолчанию. Любая уничтожающая данные операция — только по прямому разрешению пользователя и после разбора последствий.
8. Поддерживать краткие `docs/DECISIONS.md`, `docs/STATUS.md`, `docs/API.md`, `docs/ERD.md` по мере реализации. Описывать архитектуру простым и проверяемым языком.
9. После одного завершённого инкремента **останавливаться на контрольной точке**, показывать результат и следующий предлагаемый шаг. Пользователь решает о продолжении, если не дал разрешение на целую фазу.

## Субагенты и качество
- Правила ролей: `docs/AGENT_ROLES.md`; описания проекта: `.codex/agents/*.toml`.
- Если Codex не видит custom agents, сообщить об этом и использовать встроенные средства делегирования или последовательную ролевую проверку. Не писать фальшивый отчёт об их запуске.
- Агенты наследуют разрешения родительской Codex-сессии; текст «не редактировать» в instructions не равен технической песочнице. Главный агент контролирует реальные изменения.
- Проверить доступность версий Python/Django/библиотек перед установкой; не использовать устаревшие команды только потому, что они встречаются в предыдущем прототипе.
